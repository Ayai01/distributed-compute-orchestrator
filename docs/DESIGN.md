## 责任与代码入口

DCO 管调度、授权、任务与传输；调用工程管测量、评分、唯一设计预算、模型和科研缓存。任务中声明能力和资源，中心选择执行设备；运维显式选设备并使用操作员令牌。

| 模块 | 责任 |
| --- | --- |
| `cli.py` / `startup.py` / `terminal.py` | 参数、可见终端检查、服务托管与重载 |
| `commands.py` / `console.py` / `view.py` | 命令语义、键盘交互、看板格式 |
| `coordinator.py` / `allocation.py` / `admission.py` | 中心队列、份额/资源授予、有限提交窗口 |
| `worker.py` / `process.py` / `resources.py` | 执行端任务、进程树所有权、CPU/RAM资源 |
| `client.py` / `tasks.py` / `machine.py` | SDK、任务构造、操作员机器接口 |
| `bundle.py` / `cleanup.py` / `cache_*.py` | 内容资产、生命周期回收、手动科研缓存同步 |

入口顺序为可见终端检查 → 加载设备配置 → 托管服务；一次性命令和测试走对应短路径。中心和 worker 的本地配置、运行状态各自持有，源码更新不覆盖它们。

Windows经典控制台检查自身窗口可见性；Windows Terminal默认终端委托将真实窗口状态同步到本会话的伪窗口，因此优先读取该状态，不要求UI进程位于cmd父进程链。旧ConPTY宿主的伪窗口保持隐藏时，再检查本进程及控制台宿主祖先链中关联的可见经典控制台或Windows Terminal窗口。聊天应用、编辑器主窗口及无关终端窗口不作为本终端可见的依据。此检查同样用于托管服务子进程。

Windows服务子进程及独立操作看板接收`CTRL_CLOSE_EVENT`，通知现有主循环退出，并在系统关窗期限内给正常`finally`清理保留4秒。中心通过原取消链结束本中心任务，worker回收自有进程与临时物；`--url`看板只清理自身操作。正常Ctrl+C交互保持原行为，不增加轮询监护。

POSIX服务入口把`SIGHUP`和`SIGTERM`接入同一退出事件，退出时恢复原信号处理器。终端挂断后沿已有取消链保存原任务结局并释放资源，不遗留脱离终端的原生计算进程。

headless/no-browser仅控制浏览器弹页，DCO没有浏览器入口，接受该统一选项时不改变终端看板。关闭看板由独立no-dashboard选项控制，日志、可见终端、服务与任务生命周期保持。

## 工程接口边界

工程客户端只表达通用算力需求：`requires` 能力标签、`cpus/max_cpus`、`memory_mb`、`resource_share`，以及有界的 `priority`、`queue_ratio` 和 `single_thread_weight`。`resource_share` 为 `(0,16]`，`queue_ratio` 为 `[0,4]`，`single_thread_weight` 为 `(0,8]`，`priority` 为 `-1000..1000`。`node`、IP、节点权重、节点预算和完整 `/health` 只属于 DCO 操作端；操作端令牌保存在中心状态目录，普通工程令牌不能提升权限。

CLI 的本机操作员令牌只适用于 `127.0.0.0/8`、`::1` 和字面主机名 `localhost`；其他主机名即使解析到本机也按远端处理。该边界同时约束设备配置的 `operator_token` 和 `--root`/默认状态目录自动读取的令牌。远端使用显式 `REMOTE_COMPUTE_OPERATOR_TOKEN` 或 SDK 参数 `operator_token`，令牌归属该目标中心；本机启动新服务继续使用其配置令牌。

工程查看能力时使用：

```python
from remote_compute import Client
center = Client()
print(center.capabilities())  # tags/tools/CPU/RAM 的汇总视图
```

能力摘要只返回汇总标签、可用工具名称、CPU/RAM 总量与单位、以及去掉设备 ID 的加速器档案，不含设备名、URL、路径、活动任务或工程配额。大输入先用 `sync_files(..., content_id=...)` 内容寻址同步，任务只引用资产 ID；同一客户端并发准备相同内容时共享一次打包、摘要及上传，各原任务仍分别登记自己的交接引用。不同内容可并行准备，缓存缺失后沿原字节补传。不要把模型、源码或完整健康快照随每个任务重复上传。

GPU 和其他加速器使用同一套汇总能力协议。`capabilities()['accelerators']` 返回去掉设备 ID 后的能力档案，例如：

```json
{"kind":"cuda", "count":2, "memory_mb":24576, "tags":["gpu","gpu:training","gpu:general"]}
```

任务声明语义需求，不指定卡号或设备名：

```python
from remote_compute import command

task = command(["${tool:python_torch_pyg}", "train.py"], cpus=4, memory_mb=8192,
               requires=["python_torch_pyg"], project="rgcn",
               accelerator={"kind":"cuda", "memory_mb":4096,
                                             "requires":["gpu:training"]})
```

调度器按配置档案中的类型、每卡容量与标签匹配，并以整卡单元独占预留；`memory_mb` 表示每张卡须满足的最低容量，计账按占用卡数，实际显存用量由执行后端管理。卡号来自设备配置的 `ids`，同一物理卡只登记一次；配置拒绝同类型重复ID，CUDA部署使用完整GPU UUID，避免序号与UUID混登记。运行环境提供 `DCO_ACCELERATOR_KIND`、`DCO_ACCELERATOR_COUNT`、`DCO_ACCELERATOR_MEMORY_MB`、`DCO_ACCELERATOR_IDS`；CUDA 任务同时得到 `CUDA_VISIBLE_DEVICES`。worker 每次执行都从本次授权重写这些变量：无授权时分别为空、0、0、空，并将 `CUDA_VISIBLE_DEVICES` 设为`-1`。Windows实机CUDA会把空值当作未设置，明确禁用值保证未授予任务看不到CUDA设备。工程依据本任务授权选择后端。训练、GPU 仿真和通用 GPU 任务可用不同标签；无GPU设备配置空档案，CPU任务照常使用。

GPU档案与执行解释器一起验收：工具登记的同一解释器须具备完整数值依赖及CUDA构建，随后验证CPU无授予、GPU实际计算、数值等价和结束释放。调用方在授予后选择逻辑`cuda:0`，批量复用驻留模型和数据，按完整阶段计时，包括准备、数据搬运、输出及检查点；单个矩阵核的速度不作为工程加速依据。小批NumPy搜索、SPICE及RTL保持原CPU路径，后端选择不更改研究输入、预算或已接受任务。

兼容CPU执行的任务先检查中心是否声明 `accelerator_fallback`，再在同一份 admission/任务 `accelerator` 对象中加入 `fallback_after_seconds`（有限非负秒数）。该字段由调用方显式提供；省略时保持强制加速器。无匹配在线GPU时立即改为CPU；仍未派发的任务到达队列阈值时改为CPU，同一任务ID、请求包和输入摘要保持不变。首次派发后执行选择冻结，重试和恢复沿用该选择。CPU回退回执含 `accelerator: null`、原需求 `requested_accelerator`，以及 `accelerator_fallback: {"reason":"unavailable"或"queue_timeout","at":Unix秒}`。admission 的 `fallback_capable_cpus` 表示CPU路径匹配的在线预算。

ARH 的 `tensor_backend=auto` 声明一张CUDA卡和30秒阈值；旧中心未声明上述能力时，ARH提示并以CPU执行。显式 `torch_cuda` 省略阈值、保持强制GPU。DCO负责授予资源，调用工程负责CPU/GPU计算路径及结果身份。

默认中心地址为 `http://127.0.0.1:26133`。auto 模式检查本地服务角色，只有 worker 时按调用工程的独立模式规则执行；连接其他中心使用工程支持的显式 URL。这是入口部署选择，科研任务仍向中心声明能力，由中心选择全部兼容设备。中心模式下，工程 workers 上限不参与 CPU 准入；有限提交窗口准备工作，实际 CPU/RAM 由中心授予。

每个工程设置 `resource_share`（默认 1.0），中心按活跃工程的相对权重分配整数线程，用最大余数补齐余量。例如可承接54线程、三个工程同权且需求充足时为18/18/18；两个工程权重2:1时为36/18。不能整除时，例如53线程、三个工程同权，为18/18/17。份额和预取按实际匹配能力计算：工具、能力标签、共享路径和RAM不匹配的供给不抬高项目目标。需求不足的份额供其他待运行任务使用。目标、需求和占用统一按当前在线调度范围计算；离线节点原授予及尚未实际重接的恢复任务留在原记录中，实际重接后恢复占用，不以旧占用阻塞在线固定整组的空核积累。暂停但仍持有在途任务的在线节点继续计入其现有占用。

单线程 SPICE 任务声明 `cpus: 1`。可并行的整轮任务声明 `cpus: 0`，中心按工程份额和可用节点授予实际线程数，并把 `${cpus}` 传给程序。`max_cpus` 限定任务有用的并行规模，同时约束初始自动授予和后续借核；省略时沿用节点上限。`cpus: 0` 由中心处理，直接 worker 任务需声明正整数。整轮任务在单个节点执行；公平轮先安排各工程能运行的固定任务，自动任务最多等待一秒凑齐目标，之后可用部分授予启动。支持协作借还的同步内核可在安全批次边界调整授予，其余在途计算保持原授予；工程端不提交节点约束。

互相独立的方法搜索或候选块分别提交，不因后续统计配对而绑成同节点整组。串行任务使用 `cpus: 1, max_cpus: 1`；有可并行内核的任务可从1核进入，设置有限 `max_cpus`，在池与在途结果收齐后按实际授予逐步借还。内存按该任务及阶段的实测峰值留余量，源码、模型与参考资产独立复用；保留完整搜索边界，避免逐个体或逐次求值产生细碎传输。

原请求为`cpus: 0`，或`max_cpus`大于初始`cpus`时，任务按可扩核任务调度。低核启动仍只预留实际初始核数；adaptive/balanced优先将可扩核任务分散到没有DCO任务占用的兼容设备，再按负载、速度和权重选点。设备都已占用时沿用负载策略。同一物理设备的多个端点合并判断占用；固定核数与round_robin保留原选点规则。

可扩核任务在安全阶段边界请求的有限核数同样参与协作分配。`max_cpus`只设上限；正整数启动的任务在首次请求扩核前按初始核数计入需求，`cpus: 0`则已声明自动授予。中心先为就绪固定整组安排完整宽度，再在本工程各可扩核任务的有效需求间分配剩余份额；新增任务需要核数时，由已有任务在下一次借还边界让出。归还至1核后，`admission(job_id=...)`按下一阶段的可用资源给建议。重连和重试从原请求恢复任务类型，实际授予不改变其可扩核属性。

份额缺口足以承接整组且内存、工具和加速器已就绪的固定多核任务，在一个合适节点积累刚释放的线程，防止它们被其他工程的小任务连续借走。每个等待工程至多选择一个节点，其余设备继续派发；同优先级优先补足当前占用/权重较低的工程，更高优先级可继续使用空闲线程。等待内存或能力不匹配的任务不保留CPU；取消、份额变化及资源变化在下一次调度时重新计算。现有任务自然运行到结束，整组线程数造成的整数差额仍按借用规则处理。

自动线程任务按每台候选节点的实际容量计算所需线程；较大节点忙碌时，可在空闲的小节点取得相应授予。同优先级、同固定/自动线程模式的就绪任务，先安排可运行设备较少的任务，把其他设备留给适用范围更广的任务。

调用工程通过`capabilities()`或`health(brief=True)`识别汇总协议能力，再用`admission`/`window`按requires声明工具及实验环境。能力名称在请求与设备两侧统一转换，例如`ngspice47`与`ng47`等价；历史平台命名运行时别名只在迁移边界归一为`python_numpy`，不再发布为平台能力。`capable_cpus`是匹配能力且可接单的在线预算，排除暂停设备及线程数不足以承接固定任务的设备（0表示暂无供给）；`target_cpus`是当前工程份额，查询不登记活跃需求。科学缓存按物理输入、明文引擎族/主版本、执行/测量协议和容差复用。工程不枚举nodes、不绑定设备名，也不读取分配详情，设备配置与选择由中心管理。

能力与执行引擎不生成或保存哈希，科研回执和科学缓存也不记录引擎哈希或其派生分区。`ng47` 是唯一语义能力名，旧 `ngspice47` 归一到该名称。工具注册、任务和准入拒绝哈希或 OS 选择标签；worker 不把操作系统发布为科研能力。执行兼容性由明文引擎族/主版本、执行/测量协议和数值容差确认，兼容设备共同参与。源码（含生成RTL）、PDK、模型和输入内容摘要继续承担数据身份、传输完整性与资产复用；不得将其反向变成设备选择条件。

能力按实际执行环境和工具划分。新增算法使用同一解释器时，把所需包纳入该环境的完整性校验，不按算法重复登记能力。PDK 等材料通过内容资产或共享路径提供，不把目录伪装成可执行工具。迁移重复别名时保留已接受请求及原 ID 恢复所需的旧绑定，调用方迁完且原任务收齐后再退役。

Python 环境及旧名映射见 README。`requires`、命令、参数和环境中的工具模板使用同一别名规则匹配可用绑定；只比较原始工具键会错误排除兼容设备。能力汇总去重，但历史回执保留已接受的实际 Python 绑定名称和路径，避免把不同解释器的来源合并覆盖。SDK 也规范化旧服务的能力汇总，允许忙碌实例在下一次空闲重载前继续执行原任务。

工具模板与能力使用同一语义别名表，`${tool:ng47}`和旧配置键可互通。命令首项保留完整argv前缀，路径/环境变量仅接受单可执行文件绑定；优先使用同一语义能力的可用绑定。登记允许的加号、点、连字符在模板中保持相同语法。

任务进程内部继续调用 Magic/Netgen 等工具时，读取 DCO 注入的自身执行记录，保留其中 `tools[工具名]['argv']` 的完整前缀：

```python
identity = os.environ.get('REMOTE_COMPUTE_WORKER_JOB_ID') or os.environ['REMOTE_COMPUTE_JOB_ID']
record = json.loads((Path(os.environ['REMOTE_COMPUTE_JOB_DIR']) / 'result.json').read_text(encoding='utf-8'))
assert record['id'] == identity
binding = record['tools']['magic']
assert binding['available']
subprocess.run([*binding['argv'], *arguments], check=True)
```

该记录由 worker 接收任务时保存，任务只读取自己的目录及 ID。单路径是长度 1 的前缀；命令向量中的解释器、运行库适配器和固定参数一并保留。`REMOTE_COMPUTE_URL` 是资源协商/状态回调入口：独立 worker 可指向本机 worker，hybrid 则指向中心的公开视图，公开状态仅提供工具可用性，不承诺工具路径。进程内工具调用统一使用自身执行记录，端口和设备仍由 DCO 管理；命令路径仅用于本次执行，不进入科学身份或缓存分区。

中心声明`admission_job`时，`admission(project, job_id=原任务ID)`返回该任务的`recommended_cpus`、`current_cpus`、`current_memory_mb`和`available_memory_mb`，供阶段边界先判断是否值得调整工作池。此查询不改变授权；需要调整时排空当前池，再调用`resize`并按实际回执建池。运行中的worker任务通过同一lease通路查询。

`queue_ratio`（默认 1.0）控制提前排队比例。`Client.admission()` 返回当前窗口及 `max_in_flight` 安全上界；`Client.window()` 每秒至多刷新一次当前份额和上界，节点新增、能力登记和预算变化都会反映到窗口：

```text
固定线程波次槽位 = max(1, sum(floor(各设备份额 / 单任务线程)))
有上限的自动线程波次槽位 = max(1, sum(ceil(各设备份额 / max_cpus)))
预取任务 = ceil(完整波次槽位 × queue_ratio)
提交窗口 = 当前运行槽位 + 预取任务
```

整轮 `cpus: 0` 未设上限时，初始运行槽位为取得份额的设备数，至少为 1；设置 `max_cpus` 时逐设备计算完整波次。例如24、30、96线程三台设备和`max_cpus=96`需要三个任务覆盖；固定线程任务的零散余量也按设备分别计算，不跨主机拼接。自动任务在编译后归还线程时，窗口计入仍在运行的任务，按目标剩余线程和设备空闲槽位补充下一波；预取数量继续按完整波次乘`queue_ratio`计算，避免把每个已退核任务再乘一次排队比例。最大窗口覆盖每任务退到1CPU的情况，工程端提交池应允许窗口增长，实际待处理数量始终受`window.current()`约束。两台节点都可承接时，`queue_ratio: 0`也可同时提交两项整轮任务。CPU、内存、工具、能力标签和共享路径仍决定实际派发；提交窗口不是CPU授权，也不是服务端全局队列硬上限。工程只预取已就绪工作，保留搜索批次和代际边界。已启动的旧控制器和在途任务在自然边界更新。

配置位置：AOP 原运行配置、ARH-DSE、Bench 顶层使用这两个字段；AOP 规范化配置在 `execution` 中映射，RGCN 放在 `resources` 中。

```json
{"resource_share": 1.0, "queue_ratio": 1.0}
```

AOP 按角点、RGCN 按候选/PVT、Bench 按算法与种子预取。原动态窗口调用方按上界创建有限线程池，按当前窗口限制已送中心且未收齐回执的任务；本地准备future另有队列界限，AOP为2×maximum。显式ready_tasks的控制器使用小型准备/提交池和一个批状态采集循环，准备深度不决定线程数；pending及背压见[提交与查询窗口](#向中心提交与查询窗口)。长任务等待期间也定期补位，其他工程结束后可扩大原动态窗口。窗口缩小时已接受任务继续完成。RGCN 按输入顺序返回结果。ARH-DSE 整轮进入中心，轮内保留原生请求队列与构建复用机制。

Bench 默认每种子声明 1 CPU，由动态窗口决定并发，不受工程 workers 限制。同步Class-AB物理批次和方向输出内核在计算前借线程、finally归还至1；任务尾部可继续借用其他任务释放的线程。`remote_compute.max_task_cpus`可设单任务借用上界；异步求值池在启动前申请固定额度，pending收齐后归还。`remote_compute.task_cpus`指定初始额度，0表示中心初始自动授予；关闭顶层`adaptive_threads`后保持固定额度。取消批次会停止后续提交、取消并收齐已接受任务。

节点 CPU 预算、硬上限和内存配置见[算力控制](../README.md#设备预算与配置文件)。看板同时显示各工程的权重、目标份额、已分配线程和排队数。焦点刷新只影响终端展示，后台调度和资源探测持续工作。状态读取使用终端内单一后台线程，同一时刻最多一项读取；沿用聚焦1秒、失焦5秒的刷新节奏，不叠加查询。主交互线程用最近完整快照处理输入、翻页和尺寸变化，慢读超过2秒显示读取提示；失败保留原画面并显示错误，恢复后替换快照。首份状态尚未返回时也绘制等待行和命令栏，关闭看板不等待慢读。SDK首次借还资源用`health(brief=True)`协商协议和能力，省去设备历史与看板内容；旧服务忽略该请求头时仍可使用完整响应。

## 分配策略

- `adaptive`：先满足线程、内存、工具与工程份额，优先选择预计CPU负载较低的设备。候选负载相差不足一个逻辑线程时，用相同版本人工校准基准的单线程/总吞吐组合先验，再以同类任务真实耗时校准和替代，结合节点权重与未采样节点。基准组成与持久化见下文“手动算力校准”。
- `balanced`：使用相同的 CPU 负载优先规则，接近时使用单线程/总吞吐组合先验及节点权重，不采用同标签的历史耗时。
- `round_robin`：在满足资源条件的节点之间轮询，便于固定分配实验。

负载按设备的逻辑线程数归一化，并把尚未反映在采样中的派发和线程借还立即计入：

```text
背景占用线程 = max(0, 采样CPU比例 × 逻辑线程数 - worker快照已分配线程)
预计负载 = (背景占用线程 + 当前预留线程 + 外部任务线程 + 新任务线程) / 逻辑线程数
```

同设备的多个 worker 合并计算主机占用，避免重复计入 CPU。尚未取得CPU样本时，直接按当前授权账本估算负载。整轮 `cpus: 0` 比较节点时按一个启动线程计价，选定后仍按可用线程和工程份额授予。采样中的在途任务已包含在 CPU 使用率内，用当前账本替换其旧授予；连续提交不用等待下一次采样才更新负载。CPU 使用率参与节点选择，线程和内存预算决定准入；其余设备已满且该设备仍有可用额度时，可继续派发。`node` 仅供操作员运维和设备验收使用；科研任务按能力选点，已运行任务保持原节点。

任务可设置 `single_thread_weight`（有限正数，默认1），也可用 `run/spice/rtl --single-thread-weight`。这项设置只决定负载接近时选哪台主机：1对单线程延迟和并行总吞吐无明显偏向；2适合串行仿真占主导的任务；0.5适合大量独立评价的搜索。它与工程份额 `resource_share`、排队顺序 `priority` 分开，不增加线程、不改变正在运行任务的节点。单线程占比为 `w/(1+w)`，按该占比组合归一化的单线程分数与配置线程下总分的几何均值；节点weight保持生效，adaptive的同标签实测耗时校准该先验。每节点只保留最近完成的256个精确标签，普通节点快照只给条目数，不传历史耗时字典。balanced使用相同负载和算力先验、不学习历史；round_robin保持轮转。缺少同版本原生总分时仅按可用配置槽数估计总量；单线程分数不全时该分量保持中性，旧哈希/解释器分数始终不参与比较。

中心 `Client.capabilities()["capabilities"]` 包含 `single_thread_weight` 时，适配器可传此字段；旧中心省略它。普通默认1任务保持原请求格式；中心保留偏好元数据，并在派发时移除该中心提示，已有worker无需重启即可执行。启动原生估算的单线程结果位于 `benchmark.single`，使用同一混合工作单位；CLI以“单/总 Miter/s”展示。

中心直接连接设备IP的26133端口；HTTPS节点同时配置`ca_file`。worker通过本地lease接口提交CPU/RAM请求，由中心现有连接取回并授权，无需worker反向访问中心。可用`center.control(add={"name":"compute-linux","url":"https://203.0.113.42:26133","token":worker_token,"ca_file":"worker.crt"})`加入。节点配置和令牌保存在本机`nodes.local.json`，不放入聊天或Git。旧反向回调入口已退役。

局域网按实际TCP对端的回环、[RFC1918](https://www.rfc-editor.org/info/rfc1918/)私网、[IPv6 ULA](https://www.rfc-editor.org/info/rfc4193/)及链路本地范围判断，默认免令牌；`trusted_networks`仅缩小免认证范围，空列表关闭该豁免。公网和其他非局域网请求必须使用HTTPS与非空有效令牌，SDK发送凭据前拒绝公网HTTP；服务端不采用转发头声明的地址。中心操作员角色继续校验独立令牌。`add host[:port]`默认26133，省略协议时LAN选HTTP、公网选HTTPS；已登记同地址的HTTPS证书及凭据直接复用。显式公网HTTP仍拒绝。握手后按实际名称/地址去重，保留预算和原任务；保存配置不将中心令牌填入无凭据的节点。

公网初始化由`setup-https`一次性生成缺少的本机证书/节点令牌，合并保存设备配置并导出私有连接文件，私钥留worker；空闲重载继续使用既有`/restart`和原可见终端。连接文件只按其完整URL应用，多个映射端口不共享认证材料。主机名是显示名称；自动重连比较已有`machine_id`的硬件段，缺少机器标识的旧端回退原名称核对。当前Node对象、路由名、预算和原任务引用保持，新名称保存为别名；启动握手改用当前主机名时将旧名保留为别名。该过程不新建身份文件、监护或网络往返。

启动参数优先级为显式CLI、本机忽略配置、内置默认值。运行时`cpus 0`同启动时一样使用设备CPU上限并保存自动模式；中心routing.limit仍可独立限制准入，操作回执同时显示配置和有效预算。显式强制校准绕过并失效普通缓存，常规校准结果最多缓存16项。角色、监听地址/端口、CPU/RAM、工具和路径不写设备专用源码；`worker.local.json`、`nodes.local.json`、便携Git等工具、凭据和运行态均在Git忽略范围内。

节点`timeout`默认10秒，跨网慢连接可通过`control(node=名字,routing={"timeout":120})`在线调整。任务SDK通过`REMOTE_COMPUTE_TIMEOUT`继承连接时限，显式指定超时的客户端保持原设置；计算执行时限仍由`task.timeout`控制。

中心并行探测设备，启动首轮最多等待1秒；未就绪节点保持检查中，由后台继续探测，已就绪设备先提供看板及能力。单设备控制与新增设备只同步刷新对应节点，其它离线节点的探测继续在后台；控制返回后，该设备的新工具和预算已进入匹配视图。

同一任务的资源调整串行处理，网络调用不持有中心或资源池的全局锁。增加的CPU/RAM先占额度，缩减的额度等worker确认后归还；实际授权未变化时直接返回。回执丢失后查询原任务，暂时无法确认的增加额度继续保留，直到下次确认或任务正常结束，避免重复分配和退出泄漏。

宿主健康采样暂时不可用时，新增物理RAM余量按0处理；任务仍可维持或归还已经取得的额度。同机多端口只从健康端口取物理余量，但全部端口尚未反映到采样的预留继续计账，包括暂时探测失败的端口。恢复采样后，原任务按正常租约继续申请，不创建替代任务。

旧中心在RAM归还时若返回已知的空min错误，任务侧SDK只做一次原worker任务的新鲜状态查询：确认仍running、CPU与请求完全一致、现有RAM足够后，返回确认的原额度，并标记`resize_applied=False`和原错误；不伪称已归还，也不重复租约。此兼容仅限worker lease的同CPU固定RAM缩减；CPU变化、RAM增长、线性模型、终态及其他错误保持原失败。新中心修复正常生效后不进入此路径。

自动任务的初始授权不是后续并发上限。池/原生进程已收齐的阶段或自然批次边界可调用 `client.resize(id, 0, memory_mb=下一阶段总MiB)`，重新按当前所选节点预算和工程份额申请，实际CPU仍受`max_cpus`限制；以返回的`cpus`、`memory_mb`重建或调整池，再启动下一批。`resize_auto`能力表示支持0；显式正数仍表示有用CPU需求。缩减到1后也保留自动需求意图在调用工程内，下次边界再次申请，中心不在后台改动运行中的池。

RAM随并发线性增长时，使用 `client.resize(id, 0, base_memory_mb=1024, memory_per_cpu_mb=512, memory_limit_mb=8192)`；这表示下一阶段的基座+每CPU需求，中心结合当前CPU/RAM和可选RAM上限，一次返回匹配的授权。系数模式与固定总量`memory_mb`互斥；`resize_memory_model`能力表示支持。SDK面对缺少能力的旧中心保留当前授权并返回`supported=False`，调用工程按旧路径运行。同步内核完成后可归还资源，异步在途工作继续使用已有授权，只在自然收齐边界更新，不强制排空来改变算法执行次序。

设备地址显示实际节点URL的IP，`local://`私有worker显示本机。可通过`control(node=名字,routing={"host_ip":"203.0.113.42"})`补充展示IP；它不改变连接地址。

worker 默认将 `OMP_NUM_THREADS`、`OPENBLAS_NUM_THREADS`、`MKL_NUM_THREADS`、`NUMEXPR_NUM_THREADS` 设为此次线程授予；任务 `env` 显式指定的值优先。例如外层并发处理多个候选时，可将这些数值库设为 `1`，避免嵌套并行；编译仍使用 `${cpus}`。外层任务与内核线程共同使用此次授予。

任务还可设置 `priority` 和 `requires`。较大的 `priority` 先启动；`requires` 要求汇总能力标签全部匹配。节点自动报告 Python、ngspice、Verilator 等可用工具，调度器据任务使用的工具筛选供给。`resource_share`、`queue_ratio`、`single_thread_weight` 有界且只影响中心内部公平、预取和近负载先验，不能指定设备或绕过 CPU/RAM 准入。

中心与直连 Pool 按任务 ID 区分本方预留和外部任务；慢健康快照中的旧授予不再占用第二份额度。新 worker 声明 `memory_accounting=rss`：首次进程树采样前及未反映到健康快照的派发按申报量预留，采样后按当前 RSS 记账；设备预算与系统实时 8GiB 可用余量共同约束新任务准入。旧 worker 沿用其预留规则，允许逐节点在空闲边界更新。任务取消只向 worker 发送一次请求，随后按正常间隔等待终态；空队列由新任务与资源事件唤醒。

用 `label` 区分电路、保真度或相近工作量的批次，使同类耗时具有可比性。执行中的任务保留原节点。短暂断连时保留原任务ID和资源预留，状态中的 `connection_error` 显示连接问题；重连后继续查询该任务，不重新执行。已知节点暂时离线时，匹配该节点的待执行工作继续排队，其余在线节点照常服务。

`project`表示来源工程；`label`使用能表达对象、方法/阶段及必要预算的最简信息，例如 `TSA s06 FIBER 12k`。seed只显示后两位等特征位；完整seed、运行ID、路径及内容身份保留在请求/回执。同类任务保持稳定标签，便于耗时校准。看板对旧长标签只压缩展示，不改原标签、输入或科学身份；`jobs ID`及任务API显示完整记录。

健康接口在节点离线时仍返回有效响应；重启后待重连记录先恢复任务元数据，健康和资源视图不依赖worker已经重连。上游通信失败返回HTTP 502。历史版本或中心重启留下的 `interrupted` 任务可直接按原ID `fetch`：worker仍在运行时暂缓领取，完成后以worker的实际结果恢复中心记录。调用工程保留已接受的ID，避免因超时改在本机重复启动。

每个连接池共享最多8条连接，大上传及二进制传输最多占7条，为健康、状态及资源回执保留通路；同类请求按FIFO等待，已占满传输份额的请求不阻挡控制请求。本地排队默认不设网络deadline，取得槽位后才按Client.timeout约束网络读写。显式Client(pool_timeout=秒)可限制本地等待，此时PoolBusy表示尚未发送请求；调用者保持原ID和授权等待或取消。差网络下，运行中的简要状态复用不超过2秒的已有worker健康快照；终态仍实时读取。现代连接空闲10秒回收，正在传输的请求不受此空闲限制；旧客户端使用显式Connection: close，保持其POST兼容性。中心按节点串行取回结果，同ID请求合并到作业目录中的一份原ZIP，领取删除作业时一并清理。二进制GET使用Range/ETag续传，断线保留当前请求内已收字节，最多4次尝试；ETag变化时重新取完整结果。任务提交、取消和内容寻址资产上传按原ID安全重试，避免重复计算；资源调整超时先按原ID确认授予，不自动重发。

二进制上传保留明确的Content-Length并以64KiB分块写入，减少繁忙中心的GIL交接与小块系统调用；连接超时分别约束各块写入及响应读取，整包持续上传可超过该时限。资产按内容哈希在各节点缓存；缓存revision变化只失效存在记录，在途同哈希上传继续共用一把锁，等待调用者结束后回收锁。上传丢失回执时，先用原有GET确认exists，服务端校验内容哈希并发布成功后才返回存在，已收到的资产直接复用；真正未收齐或确认失败时，仍以同一内容ID从头重发。依赖同一资产的任务共享上传，完成后继续原任务派发；结果下载沿用Range/ETag续传。

任务POST丢失响应或旧服务受理后通知误返HTTP 404时，SDK先GET原ID，并核对回执中的ID及原请求包`request_sha256`。匹配时直接返回该回执，保留其实际queued/running/终态结局，不重发请求体；404无法确认匹配则保留原错误，不重发POST，其他传输中断沿原ID继续原有有限重试。摘要仅在异常响应后的核对阶段计算一次，不对正常提交增加哈希。提交通知直接使用已受理回执的project/label，不再次读取可能正归档或已领取的任务记录。中心完成作业发布后，接收阶段的资产引用由现有作业接管，释放临时接收引用只持状态锁，不再等待全局资产缓存I/O。

派发前取消会退出连接槽及共享资产锁的等待。没有其它已派发任务需要时，分块上传停止且不自动重传；仍有消费者的共享上传继续完成，已取消任务随后退出，不发送任务POST。明确尚未发送任务的取消回执保存在中心，记执行CPU为0，领取时不向worker请求不存在的结果；任务POST回执不确定时仍先核原ID，保留既有取消与费用规则。

Client.fetch与中心向worker取回原ZIP统一调用Client.artifacts，复用各自独立的结果Client和连接池；两跳下载的响应头与接收空闲超时均至少120秒，节点状态/提交沿用原短超时，调用工程无需改调用方式。中心首次返回结果头之前先取回远端ZIP。排队等待时发现调用端已断开，就放弃该次排队取回；已经开始的有效传输仍完成并留下缓存。正常持续收数不以总耗时截断；失败保留原任务和结果，之后仍用原ID领取。

已完成结果领取、原任务等待、只读准入建议、资产存在性查询，以及resize前的能力读取和原授予确认遇到502/503或连接中断，共用`max(120, Client.timeout)`秒的有限重连窗口，间隔从0.2秒退避到5秒；404及权限等永久错误直接返回。`wait_timeout`仍使用调用开始时的原绝对截止。`Client.has_asset(id, job_id=原ID)`只查询同一资产并保留原生产者交接头；`sync_files`的冷/暖存在性检查均使用该入口，恢复冻结ZIP的调用方也可直接使用。查询恢复不会再次准备、打包、摘要或上传已经存在的资产。实际resize/lease变更不因此重放，能力或授予确认成功后才返回可用资源。原任务执行预算、结果及CPU费用保持；提交和实际资源调整沿各自的原ID/回执契约处理。

`Client.wait`用简短状态读取，默认最短`poll=0.15`秒、最长`max_poll=5`秒。同一`status/phase`持续的秒数除以20作为间隔，并截在上述范围内；状态或已报告阶段改变时重新从短间隔开始。两三秒任务保持原节拍，长黑盒逐步减少查询；显式令`max_poll=poll`使用固定节拍。每次睡眠受原绝对期限限制，终态再读完整原ID回执。可选零参数`cancel`回调在读取之间以及本地等待/重连退避中每0.1秒检查，返回真则抛出`RequestCancelled`并结束本地等待；正在阻塞的HTTP仍沿用原连接超时。它不提交、取消、删除或改变远端任务，调用工程继续决定原ID的后续处理。等待复用当前线程和核心重连，不另开监护或服务端状态副本。

工程份额按各请求实际可运行的节点计算加权整数最大最小分配，含固定节点、工具、共享目录和CPU需求上限；同一节点的线程不会同时算给多个工程，只计算本任务实际兼容的设备预算。单节点沿用最大余数，多个节点用逐线程增广补齐可行份额。admission、排队分配和阶段增借使用同一份额；任务在关闭旧池后的cpus=0请求会按当前份额重新授予，包括归还超额CPU。已运行池保持原授权直至调用方发起安全阶段协商。

Windows新建作业目录设置可继承的Low完整性标签，允许现有带Low标签的firtool、GSIM等工具写入本作业的输出和TEMP。处理发生在解包和创建子目录之前，使用Windows原生API；原DACL及继承标记保持不变，现有作业、父目录、共享盘根和工具文件保持原样。Linux沿用普通目录逻辑。
操作员视图中的工具变体包含节点名、可执行入口和可用性，不包含引擎文件哈希；普通工程工具视图只表示可用性。科学输出使用明文引擎族/版本、执行/测量协议与容差。

## 现有工程接入

### 向中心提交与查询窗口

```python
from remote_compute import Client, command

center = Client()
window = center.window("my-project", resource_share=1.0, queue_ratio=1.0, cpus=0, max_cpus=8)
print(window.maximum, window.current())
task = command(["${tool:python}", "runner.py", "--workers", "${cpus}"],
               cpus=0, max_cpus=8, memory_mb=1024, project="my-project", resource_share=1.0,
               outputs=["measurements.json"])
result = center.run(task, inputs="my-batch")
print(result["status"], result["cpus"])
```

同一工程的任务保持相同 project 和 resource_share；工程内任务优先级用 priority 表达。多个生产者共用一个控制器及 pending 计数，中心统一控制执行资源。

`admission/window(..., ready_tasks=N)` 显式指定整个工程已经提交、尚未持久发布并收齐的任务上限，N为1–4096。它与执行核数分开；中心仍按能力、公平份额、CPU/RAM/GPU决定实际启动量。不设置时保留原 queue_ratio 动态窗口；设置后 in_flight/max_in_flight 为N，queue_ratio 不再决定准备深度。此值是控制器的提交约定，不是一次资源预留。`running_tasks/queued_tasks` 是窗口内的执行/准备建议，`project_active_tasks` 仅为中心当前非终态数；它不代表消费者尚未发布的全部结果。

`window.available(pending)` 返回 `max(0, window.current()-pending)`。pending 由工程在提交前登记稳定原ID，受理结果未明、排队、派发、运行及终态尚未发布的ID均占一个位置；原结果持久发布、费用入账并清理远端后再移除。缩小窗口只停止继续提交，保留已受理工作。准备中的本地输入另设小上限，不提前生成整个未来研究批次；不把256个准备位置变成256个轮询线程。多个控制器不能各领一份完整工程窗口。

```python
window = center.window("my-project", cpus=1, requires=["python_numpy"], ready_tasks=256)
credits = window.available(len(pending))  # pending 从本工程持久恢复账本载入
states = center.statuses(pending)         # 一个调用只查询这些原ID，不读全量jobs

# 原控制器收集循环；publish_to_project 是宿主已有的持久发布/费用入账步骤。
for identity, state in center.wait_any(pending, wait_timeout=30).items():
    receipt = center.fetch(identity, delete=False)
    publish_to_project(identity, receipt)
    center.delete(identity)
    pending.pop(identity)
```

`statuses(ids)` 返回按原ID索引的简要状态，每次请求最多128个，较长列表由SDK分块；空列表不请求。`POST /jobs/status` 只按给定ID读取原快照及冷回执，返回进度字段，不包含日志、工具清单或全任务历史。缺失ID显示 `status=unknown,status_code=404`，不触发新提交。`wait_any` 单循环自适应等待任意终态，返回简要状态；完整尝试、实际CPU和科学结果仍由 fetch 领取。等待取消或超时只结束本地等待；unknown 留原恢复账本，由调用者核对原受理/领取事实。

`batch_status` 和 `admission_ready_tasks` 分别协商服务端支持。新SDK面对旧中心时，ready_tasks 在同一工程计数器上实施，CPU/RAM/GPU仍由旧中心准入，reply 的 ready_source 为 sdk_legacy；批状态回退到已知ID的 brief读取，不访问全量jobs。服务升级后 ready_source 为 center，批状态按128合并；部署继续使用安全空闲边界。RemoteError 对HTTP和传输错误都提供 status_code 与 transport_retryable：HTTP为实际状态码，传输无HTTP码时为None；只读查询可沿既有有界重连恢复，受理身份和科学重算由原协议判定。

### 同步内核在阶段边界借还资源

全中心 `control(paused=True)` 只暂停新任务派发，已运行任务仍可按原 ID 在安全边界 `resize`；节点 worker 的 `paused` 则同时限制该节点增长。全中心暂停影响所有工程的新增派发，接口自身没有 TTL 或窗口所有权；临时维护执行方负责计时、记录原暂停状态并在结束或异常时恢复。公平份额、实际可用 CPU 和 RAM 准入始终有效。

重启维护的`start_paused`在Coordinator构造时、调度线程创建前生效，消除先启动再暂停的派发窗口。它是本机的启动策略，运行期control不写回此策略。旧队列、回执和资产引用保持；恢复线程只查询/重连原worker ID，产生的重试继续排队至显式恢复。删除终态目录在同一条件锁下标记原Job已退役，晚到状态/重试不再写盘或复活目录；目录释放复用不跟随链接的remove_owned。

已确认的阶段增长需求若因满载只得到部分授予，后续派发为其保留节点公平份额内新释放的空核，避免空核持续被其它排队任务重新借走；从固定1核进入后显式增核的任务也参与。计算保护量时沿用同工程就绪任务分配和原阶段内存模型；较高优先级任务仍可派发，内存不足的增长不锁住空核。降低需求、取消或结束后立即解除保护。保护不修改活动池或 worker 授予，调用工程在下一次池已关闭的安全边界通过原 ID 的 `resize` 领取；这些空核在领取前可暂时空闲。

worker 任务环境提供 `REMOTE_COMPUTE_URL`、`REMOTE_COMPUTE_JOB_ID`、`REMOTE_COMPUTE_TOKEN`、`REMOTE_COMPUTE_HOME`，支持时 `REMOTE_COMPUTE_RESIZE=1`。SDK 使用执行设备的 DCO 包；远端请求先到本机 worker 的 lease 接口，再由中心的既有轮询连接转交授权。SDK 根据 `REMOTE_COMPUTE_LEASE` 和 worker 任务 ID 路由，调用工程直接使用下面的 Client 接口。中心仅监听回环时，已配置 worker 仍可通过这条单向通路借还资源。

```python
import os
from remote_compute import Client

center = Client(os.environ['REMOTE_COMPUTE_URL'], os.environ['REMOTE_COMPUTE_TOKEN'])
identity = os.environ['REMOTE_COMPUTE_JOB_ID']
grant = center.resize(identity, desired_threads, memory_mb=phase_ram_mb)
try:
    compute_batch(threads=grant['cpus'])
finally:
    center.resize(identity, 1, memory_mb=resident_ram_mb)
```

`resize` 保留原任务ID和输入摘要，返回 `id/cpus/memory_mb/requested_cpus`。增长受工程权重、任务 `max_cpus`、当前可用线程和RAM约束；调用方始终使用实际 `cpus`。初始以 `cpus=0` 提交的自动任务，在已排空阶段申报正整数有用并行量时也参与同工程公平分配；重复当前线程数仍重新分配，申报值保持上限，归还到1核走直接路径。初始固定线程任务保留其显式调整语义。可选 `memory_mb` 在同一请求中调整内存预留，例如编译结束、子进程退出后 `center.resize(identity, 1, memory_mb=512)`。内存准入失败返回409并保留原CPU/内存授予；实际RSS仍参与准入，降低申报不隐藏真实占用。两端声明 `resize_memory` 能力后使用联合调整，旧节点返回 `supported=False` 并保留原授予。同步批次结束后才归还，异步 pending 期间维持固定授予。BLAS 内层保持1，避免与外层并行相乘。worker 与中心同步计账，取消、异常和完成均按最后授予释放；回执保留 `initial_cpus/peak_cpus/resize_count`。旧节点未声明 resize 能力时继续原授予。

SDK 的 `lease_timeout` 同时用于初始 worker lease 和直连中心的 resize，默认 `max(timeout,130)`；普通请求和 lease 答复保留普通网络期限。两种资源请求超时均不自动重发，调用方按原任务ID核对实际授权，保留原失败和费用。

任务在资源协商期间结束时，迟到的lease回执只幂等确认，不修改终态或已释放授权；等待方随任务结束退出。失败、取消与中断分别保留真实结局，避免协商响应覆盖原错误和费用。

DCO负责跨工程份额、CPU/内存准入、实际授予和原ID资源账本；调用工程负责判断是否有可伸缩内核，并在并行池/子进程已收齐的安全边界借还。YOLO包审计默认每包1CPU；对约50毫秒的串行尾段增加线程会增加通信和调度开销，较大通道块才按实测启用多核。Rocket/BOOM可在编译结束后按实际仿真并发和DDR规模同时收缩CPU/内存，ARH常驻池保持初始授予直到池关闭。工程资源配置不参与科学结果缓存身份。

RAM申报对应当前阶段仍需承载的对象和并发子进程。编译器/并行池退出且其对象释放后，联合归还CPU和RAM；下一阶段增加峰值前先申请并检查实际授予。付费账本、模型和数据仍常驻时保留其需求；DCO 保留任务申报与原请求身份，已运行任务按实际 RSS 计入设备占用，空预留可供其他就绪任务使用。`/health`的节点`active_jobs`同时提供`memory_mb`与worker最近采样的`rss_mb`，`memory_requested_mb`与`memory_reserved_mb`分别表示申报合计和当前计账量。

## 分段计算和本地持久结果

总科研预算属于调用工程，每个DCO执行是其中一个不可变工作段。按近期实测耗时和完整工作边界安排任务：合并过碎工作，将长任务拆到完整代、角点批次或检查点；通常运行数分钟至20分钟，接近或超过30分钟时调整下一段粒度，不在30分钟强制终止。工作目标、科学预算与故障超时分开。核数按当前可并行工作及内存借还，收齐后归还；同时记录准备、传输、计算、封存耗时及峰值内存，复用静态资产，只传本段必要输入和增量成果。受理、准备与网络交接开销单列，worker初始化、计算、封存和退出纳入段运行时间。已就绪工作保持适量预备；输入、依赖和预算已就绪的段才入队，依赖上一段状态的后续段按完成事件解锁。准备深度、实授资源和专项并发上限分别管理。

工程在完整世代、训练阶段或trial边界原子封存完整恢复状态，包括继续执行所需的RNG、群体/档案、模型与优化器、请求与异步信用、唯一NFE和费用游标。先用小型连续/分段对照验证下一候选、状态与预算结算一致；已付观测缓存与前沿进度另保留。既有冻结worker按实际可恢复边界迁移，原请求/执行ID留档，新段显式映射原科学任务及剩余预算。

`write_job_file(id,path,data)` 提供原子文件投递；控制路径及协作停止语义归项目worker。worker封存完成后正常退出，DCO取消/超时结束进程树。`read_job_file_changed(id,path,version)`领取原子发布版本，未变化返回304；旧端点缺版本支持时先核已有小型进度/manifest，再领取变化增量。

长期科研缓存、已消费结果和恢复账本保留在发起端。每段只准备必要输入与新的紧凑增量。`sync_files(factory,content_id=...,job_id=...)`可复用不可变身份，资产缺失才调用factory打包；`content_id`覆盖相对名称、字节与执行权限。`has_asset`核原内容存在性，accepted任务引用继续保护，`release_assets`用于放弃的输入交接；任务结果收齐仍走fetch/发布/delete。节点在已缓存且引用有效时复用同内容资产，跨节点首次按需同步，未引用资产沿原暖缓存预算回收。

段终态 `fetch(delete=False)` 后，本地持久发布原结果、恢复状态及全部费用，再 `delete` 释放任务动态目录。活跃、待领及恢复引用继续保护。缓存供应协议、实际命中、真正新增原生执行及排队/准备/求解/运输分列；已付数据的重复执行完整记账。源码/模型/输入身份在冻结和传输时核对，沿原回执复用，不逐段重打包整库或逐NFE全量hash。

## 任务文件与结果

一个任务由顺序执行的 `steps`、输入文件和输出模式组成。任何一步失败即结束该任务，保留退出码和日志。`timeout` 覆盖整条执行链。取消和超时会结束所持有的进程树，包括编译器子进程。

普通计算的 `retries` 默认2：提供者停止、原作业明确丢失或重启后报告interrupted时，中心保留原提交ID、输入摘要、种子、资产与引擎约束，重新入队；每次执行使用独立worker_id，历史写入attempts。重试不向客户端短暂公布终态，不重复归还资源。普通网络超时继续查询原任务，其他在线设备照常工作；程序报错、科学不可行、任务超时和用户取消均不自动重算。运维machine命令默认retries=0，避免文件修改等副作用重复执行。

中心和worker默认将任务、资产、回执及声明输出保存在工程 `.local/state` 普通磁盘目录；仅TMP/TEMP使用共享RAM盘。worker重启保留已完成结果，未完成结果带原ID标中断，由中心按重试预算恢复。中心重启重新连接原任务，已排队请求继续排队，已完成未领取结果仍可取回。调用工程把长期训练checkpoint、已付费评价账本声明为outputs，并在安全阶段原子发布；恢复任务沿用既有账本，避免重复已完成求值。

```json
{
  "label": "my-batch",
  "cpus": 2,
  "memory_mb": 512,
  "priority": 5,
  "timeout": 300,
  "steps": [["${tool:python}", "runner.py", "--workers", "${cpus}"]],
  "outputs": ["measurements.json"]
}
```

变量可以出现在命令参数、环境变量、`cwd`，以及 `render` 指定的 UTF-8 文本文件中：

| 变量 | 含义 |
| --- | --- |
| `${tool:python}` / `${tool:ngspice}` / `${tool:verilator}` | 节点配置的工具；多参数前缀放在每步第一个参数，单个可执行路径也可嵌入环境和输入文件 |
| `${work}` | 当前任务的独立工作目录 |
| `${cpus}` | 当前任务占用的 CPU 数，用于程序线程数或编译 `-j` |
| `${exe}` | Windows 为 `.exe`，Linux 为空串 |
| `${asset:models}` | 本任务引用的已同步只读资产目录 |
| `${shared:pdk}` | 节点预部署的共享目录 |

大模型或 PDK 可以预部署到各节点，通过 `worker.local.json` 的 `shared` 配置引用。小型模型包可以同步一次后复用：

```python
asset_id = client.sync("my-models")
task = ngspice("circuit.spice", assets={"models": asset_id}, render=["circuit.spice"])
result = client.run(task, files={
    "circuit.spice": '* deck\n.include "${asset:models}/device.lib"\n...'
})
```

资产按文件内容生成 ID；模型变动产生新 ID。提交前每项引用必须存在于中心；缺失时返回 `Synchronize missing asset first`，不创建任务或占用线程。客户端重新同步缺失资产后可用同一 ID 和原输入提交；长驻生产者在重连、重载或缓存回收后重验静态引用。节点部署路径分别配置，任务保持同一份逻辑输入。`shared` 中的预部署内容版本由调用工程维护。

任务输入和输出位于普通磁盘的持久状态根，`root/--root` 与任务 TMP 的 `temp_root` 分开。编译或仿真可重建临时物使用任务独立 TMP；客户端收齐结果后默认清理节点任务目录，显式 keep 可保留。共享资产按引用和缓存策略复用；目录参数及迁移方式见 [README](../README.md#设备预算与配置文件)。

普通计算任务继续使用独立工作目录。指定 `cwd` 的任务在目标机该目录中执行，`cwd` 接受绝对路径、`~` 或 `${shared:工程名}`；`${work}` 和 `outputs` 始终指向任务输入目录，可将需要回收的文件明确写入 `${work}`。任务 JSON 的 `stdin` 是输入包中的相对文件路径，逐步作为标准输入传入。

中心内部回执包含任务 ID、输入摘要、命令、退出码、资源、时间和工具登记快照。普通工程视图保留任务状态与本任务资源，去掉设备名、URL、工具路径和命令路径；`tools` 仅保留可用性。科学输出使用明文数值协议与容差，不生成或保留能力/执行引擎哈希。科学缓存依据物理输入、数据内容、角点与测量协议复用，不按工具构建或平台分区。接受后的任务通过原 ID 查询，相同 ID 和输入在保留期间只执行一次。

提交回应和首次查询同时遇到瞬态传输失败时，SDK在原有有界重连窗口内先查询原ID，并核对请求包摘要；已受理就直接沿原状态继续。仅查询明确返回404时才以同ID、同输入补交。请求冲突、取消及计算失败保留原结局，传输重连不增加科研评价次数。

批量状态逐个原ID返回结果。已领取任务在并发清理时消失，该项返回`unknown/404`，其余任务继续返回；SDK对旧中心由此产生的整批404只重读一次同批ID。调用工程以自己的持久终态和待领取清单核对缺失项，不重新创建已付计算。

### CPU工作量计量

显式任务环境 `DCO_CPU_ACCOUNTING=1` 复用worker的进程组/Windows Job CPU采样，累计CPU秒包含用户与内核时间；仅对实际CPU秒差分积分 `W = Σ Δt_cpu × f_GHz`，等待和空闲不增加工作量。`cumulative_cpu_seconds`是既有`cpu_seconds`的同口径别名，`cpu_accounting_sampled_at`为采样Unix时间。

中心重试按原ID保存每次已结束尝试的CPU秒、采样与频率覆盖、资源峰值和时间。顶层`cpu_seconds/cumulative_cpu_seconds`继续表示当前worker尝试；有重试时，`total_cpu_seconds`为所有尝试的CPU秒之和，仅在各次都有实测且未标记`cost_incomplete`时给出数值，缺失时为null并保留已有分项。最终回执失联时保留最后一次在线采样，标明它只是已知前缀。重试次数耗尽也保留最后一次的实际计量，不把旧回执缺测填成0；原回执、输入及科学预算不改写。

Windows用单个标准库PDH查询读取`Processor Information(_Total)/Actual Frequency`，每宿主至多1Hz且冷启动先取得完整初始区间；超过两个普通周期的空档先重建PDH基线，缓存间隔从读取完成后起算；使用英文计数器API适配系统语言。Processor Frequency及额定频率不作替代。Linux仅读取cpufreq的`cpuinfo_avg_freq`或`cpuinfo_cur_freq`硬件报告；宿主/虚拟机没有该信息时保持缺测。来源参考[Windows PDH](https://learn.microsoft.com/en-us/windows/win32/perfctrs/using-the-pdh-functions-to-consume-counter-data)和[Linux CPUFreq](https://www.kernel.org/doc/html/latest/admin-guide/pm/cpufreq.html)。频率表示宿主活动平均/策略平均的估计范围，`cpu_frequency.scope`分别标明；CPU秒的归属仍为本任务。

`cpu_frequency`保留`source/scope/covered_cpu_seconds/weighted_mean_ghz/observed_ghz_seconds`，加权均值只用已覆盖CPU秒。覆盖完整时`cpu_work_ghz_seconds`给出完整累计值，否则为null，已观察的部分仍在`observed_ghz_seconds`中。未测频率不回填当前值，旧任务不重算。每任务只保留累计量；本地result.json至多1Hz且CPU计数变化时原子发布，读取者核worker原ID和采样时间。临时Windows读共享冲突只推迟这一快照，任务和最终回执继续正常封存；不创建采样日志、线程或额外网络请求。来源及scope/覆盖量随原最终回执走现有通道，简短progress保留原字段；失败重试沿新worker尝试重置此计量。

### 失联设备与主动发现

Pool按最近一次成功健康握手的单调时钟计时，满60秒将节点标为detached并禁用路由；资源行、旧占用快照和设备通知一起隐藏，普通健康/TCP采样停止。已受理任务同时暂停自动状态轮询，保留原worker ID、输入及授予，只由核心重连握手探测；重连成功后继续读取原任务，显式取消仍沿原结算通路处理。随后每60秒进行一次健康握手，最多5次；成功后恢复原预算，五次失败后等显式add/scan。人工停用不参与自动重连。忽略配置中的reconnect保存已消费次数和下次时间，启动继续剩余次数，不重置额度。显式停用/换址改变连接代次，晚到回复不覆盖操作员决定。配置读、合并及原子写共用跨进程锁，自动重连与手动save不互相覆盖；人工停用立即持久化。

已接受任务的引用、输入和回执不因节点移出而删除；原ID的恢复与领取通路仍保留。已请求取消的任务在节点移出后以interrupted结束本地排空；重启后尚未重连的原任务收到取消时也使用此结局。两者保留remote_cancel_pending与cost_incomplete，不自动重算，也不将未知费用记为0；离线领取返回现有回执，不继续等待远端文件。重连后的cleanup先重试原ID取消，确认远端删除后才删本地记录。仅持久化该节点连接状态，保留其他设备、预算和凭据；普通人工停用节点启动时不握手。

scan为操作员显式、一次性的IPv4局域网发现：最多4096地址、32路并行，TCP可达后读取小型DCO握手，识别可接入的worker；不拉任务历史、工具清单或科研数据。已知HTTPS节点继续使用其证书和凭据，未配置目标不携带全局令牌。默认只报告，scan --add复用add的去重与原预算恢复。网络枚举和扫描不参与科研路由。

### 手动缓存交换

`sync_cache`先比较记录清单，再按最多1024条或约1MiB的批次补缺；相同清单不再导出记录，源码/模型资产继续按内容复用。科研数据交换不复制SQLite、WAL、任务认领或共享压缩布局表。

AOP交换键明文携带科学命名空间、五字段执行环境和原始角点数据ID。执行环境不求摘要；记录摘要只覆盖宽度与数值payload。目标通过生产者的`semantic_cache_units`查找或分配自己的UUID目录，保存相同`contract.json`并使用原`cache-unit`/`append`锁。仅传播kind0原始角点，聚合由目标重建；unknown版本或legacy-unvalidated协议退出可复用交换。

RGCN先由生产者解码共享布局记录，再以独立完整逻辑JSON压缩交换，保留原始数值、物理签名、角色、PVT和溯源。未知协议旧观测保持`legacy-observation-UUID`，通过固定的`observation_physical_signature`保留来源边界；仅有一个签名的旧库可使用该唯一值，多签名来源未定时留原库待判定。可同步的旧观测仍由生产者`find/cached`排除测量命中。该观测ID不是能力或引擎标识。

## 传输与本地执行

- hybrid 本机 worker 进程内调用，不经过第二层 HTTP；本机结果直接附加中心记录后打包一次。外部调用者仍统一访问中心 26133。
- 普通固定线程任务保持原始输入包直接转发；整轮自动线程任务仅在派发时写入实际授予的线程数。输入身份与重复提交语义保持。
- 模型和源码按内容标识同步；同一节点缓存版本内每份资产只检查/上传一次，并发任务共用同步锁。worker 重启或回收旧资产后重新确认；命中回收与派发的交错时，中心重新同步缺失资产并沿用原任务ID。
- HTTP 使用持久连接。状态轮询只返回进度字段，完成后取本任务资源和科学结果；支持 gzip 的客户端接收压缩 JSON，旧客户端继续接收普通 JSON。
- 文本包采用低开销压缩；已经压缩的 gz/npz/zip/7z 直接封装。仿真器构建和中间文件留在执行端，按任务 outputs 回收必要结果。

| 工程 | 默认回传内容 |
| --- | --- |
| AOP | 执行端测量与解析后的 aop-result.json；按配置选择日志。 |
| RGCN | measurement.json：指标、分析证据、波形统计及数值摘要，不传整套原始波形。 |
| Bench | result.pkl.gz：评分、前沿、轨迹等报告需要的科学数组。 |
| ARH-DSE | summary/report 与恢复、验证所需产物；保留报告校验，不回传整个编译环境。 |

通用 SPICE/RTL 命令的 outputs 由任务声明；需要原始波形时显式保留对应输出模式。调用工程的测量定义和正式产物契约保持。

声明`outputs`的任务在正常、失败、超时或取消后，Python自动删除已消费的输入、构建物及未声明的仿真原始文件，只保留声明的结果和诊断日志等待取回；未声明输出的通用任务保留原按名称读取job-file的行为，取回后一起回收。排队取消立即回收未执行的输入，退出再次收尾。待取回结果不作为垃圾清理。

worker的可重建资产按LRU管理，启动、任务取回和退出时回收未被任何在途或待取回任务引用的旧版本，未引用暖缓存目标上限512MiB，仍被在途、待领取或交接引用的资产不挤占该额度；总量可超过暖缓存目标。支持`asset_handoff`协议扩展的worker在首次派发检查/上传前为原ID暂存整组资产引用，受理后交给正常任务引用，失败或取消则由发送端释放；不等缺资产拒绝后才保护输入。检查/上传续期，失联发送者的引用闲置1小时后到期，服务退出也释放；交接不创建任务或占用CPU，只交换小型清单，不重复传已存在资产。旧worker继续5秒普通交接窗口及沿原ID补传一次的流程。worker按内容ID串行发布同一资产，校验和解包在全局缓存锁外执行；不同资产和作业受理可并行，发布、引用与回收继续在原锁内完成，闲置发布锁自动释放。健康接口的`asset_cache`提供字节数、上限和数量，统计只扫描新资产，不在刷新时遍历磁盘。共享盘的其他工程目录不参与此回收。

中心保存的未引用资产ZIP同样按512MiB暖缓存目标管理，任务/交接引用另计。临时输入可用`sync_files(..., job_id=原任务ID)`在原有检查/上传请求头中登记生产者，复用`asset_handoff`协议，无新增传输往返。相同资产的不同生产者各自持有引用；受理后转为任务引用，全部消费者领取删除后才进入LRU回收。准备放弃时用`release_assets(id)`释放，失联生产者的交接在1小时无更新后到期；超期或服务重开后提交前重新同步原冻结内容。每次上传、领取删除、显式释放以及服务启动/退出均可触发回收，不增加后台定时器。

大上传的摘要和临时文件写入、任务请求的持久落盘均不持资产缓存锁；相同资产写入按内容ID串行，原任务受理按提交锁串行。受理中的资产另有引用，生产者提前释放交接也不会在提交发布前被回收；发布后由正常任务引用接管。缓存检查、上传发布与回收在短锁段核对引用。

`admission`的运输窗口属于工程总需求。一个工程有多个采集源时共用控制器/在途计数，或串行推进原控制器，不把每份窗口当独立私有额度。自动任务的`recommended_cpus`描述本次阶段机会，实际增长继续以原ID的resize回执为准；已归还的旧需求不限制下一阶段重新借核。

未携带任务ID的旧同步请求，在本次中心运行期间继续保留，兼容旧生产者准备多份资产后再提交的行为；共享源码/模型可继续沿用该方式。旧服务忽略新增请求头，保留原缓存规则。未领取或中断待恢复的回执所引用资产始终受保护，可能超过缓存目标。中心`health.asset_cache`显示占用，`retained_jobs`显示仍待领取/处理的终态记录数量。

资产校验、写入、解包、计量与回收使用独立资产锁，调度条件锁只保护任务和引用的短状态变更。任务包准备完成后才原子受理。同一任务的结果打包、文件读取/写入和删除共享结果锁；慢磁盘操作期间状态查询与资源借还继续响应。缓存检查、交接、日志和领取清理即使只有小JSON，也使用已有的大传输连接额度，给控制请求保留同一8连接中的一个槽。健康统计只读缓存元数据，不等待资产扫描或回收。

`Client.run`、`Client.fetch`和`machine`默认在成功取回后清理服务端任务；有意保留时才使用`keep=True`或`delete=False`。任务由调用工程收齐并持久化输出后，服务端副本即可回收。服务退出负责清理自有TMP和过期缓存，未领取结果继续留在普通磁盘，重开后用原ID领取。DCO不会因任务结束或超时而自动丢弃研究回执；“不保存实验记录”应由调用工程控制正式报告，并继续正常取回清理DCO任务。

常驻记录分为活跃任务与终态索引。终态仅常驻ID、资产引用和worker原ID，完整回执保留原`result.json`，内存缓存最多64份；并发领取仍引用同一对象和结果锁。中心在这些现有记录内整体替换只读状态快照，活跃和已缓存原ID的GET不等全局条件锁及回执磁盘替换；非终态状态先发布，终态成功落盘后发布，interrupted经重试决策确认后才作为最终结果发布。冷历史状态直接读原子发布的终态文件，不等待调度锁、不另建缓存对象；缺失原ID即时返回404。成果领取在锁内使用实际记录，沿用对象及结果锁；不另建历史缓存、持久副本或后台线程。公平份额、调度、准入、RAM与看板扫描活跃集合，资产回收使用引用计数，不重复遍历历史回执。正常结束已清理的TMP不在退出时再次逐项打开历史输入；有清理错误的任务单独重试。磁盘记录、费用、attempts与未领取输出保持完整。

默认路径与迁移入口见[README](../README.md#设备预算与配置文件)。库缓存环境按任务env、设备/继承env、DCO默认路径依次取值；外部已有可用工具及模型/依赖缓存原位复用。`temp_root:null`等同缺省，优先共享RAM；普通磁盘回退仍位于DCO目录。一次性`migrate_root_from`仅在旧worker锁可取得、目标位于DCO`.local`且不存在时整体重命名；崩溃后已完成的重命名可继续，不复制数据或合并状态。

Windows共享盘初始化沿用同一个全局互斥对象，以`CreateMutexExW`申请`SYNCHRONIZE`，等待及释放保持原语义，现有对象的权限保持原样。此权限足以使用互斥锁，见[Windows互斥对象访问权](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-openmutexw)。

原生HTTPS worker支持单向资源协商：任务访问本机lease接口，中心按节点合并轮询待处理请求。存在此类在途任务时约每0.2秒检查一次，空闲节点沿用常规采样周期，避免每任务各建高频轮询连接。网络短暂中断保留原授权。

## 接入与传输约定

单次HTTP请求体上限为512MiB，SDK在发送前按最终ZIP或JSON编码体积检查；GET成果响应保持原通路。大输入可拆成独立内容资产复用，各任务沿原ID持有交接引用。

- `requires`声明实际工具及`shared:<别名>`数据位置能力，步骤以`${shared:别名}`引用；同名工程目录不代表数据已同步。冻结数据与模型作为内容资产，结果取回后由工程发布到持久目录。
- 科研工程沿用中心通路，中心内部回执保留来源设备，工程输出记录科学输入和明文执行/测量协议。身份及能力规则见“工程接口边界”。
- 只提交已就绪、能消费结果的工作；源码/模型每内容版本同步一次，重复候选复用工程现有科学缓存。连续小内核合并阶段授权，阶段结束及时归还；等待/借还耗时与CPU计算分开统计。
- `read_job_file_changed(id,path,version=None)`返回`version/data/changed`；后续传回版本，未更新返回304且data为None，中心与worker两跳都不重传文件。需要恢复状态时按原子发布批次更新，不反复下载未改变的检查点。
- 节点动态资源独立采样，慢节点不阻塞其他设备；首次连接/worker换PID取完整工具元数据，日常采样只取动态资源、活动任务和有界通知。简要健康查询直接返回身份与协议能力。
- HTTPS握手在独立请求线程内进行，沿用10秒空闲期限；未完成或无效的TLS连接独立关闭，不阻塞监听循环、新连接或已有任务。

静态大输入已有内容摘要时，复用同一个 SDK Client，调用
`client.sync_files(files_or_factory, content_id=摘要)`。摘要覆盖包内相对路径、内容和执行权限；
SDK 先确认已有资产，命中时不生成文件、不压缩，缺失时才调用零参数工厂并重新上传。
索引只存最近128个摘要与资产ID，不保留ZIP副本；不改变中心资产引用/回收规则。

## 手动算力校准

固定 `native-mixed-v4` 负载包含批量 FP64 Newton、uint32 逻辑/访存和 512×512 矩阵乘法。仅在人工执行`calibrate`或设备控制`benchmark=True`时校准，分别测60秒单线程、60秒预算线程；导入/分配/预热不计分，BLAS 内层固定 1。CPU 身份、可见 CPU、线程预算匹配时复用 `.local/benchmarks/<线程数>.json`，`DCO_BENCHMARK_DIR` 可改位置；启动、重连、资源配置变化及定期状态采样都只读取匹配缓存，不自动校准；没有有效缓存时显示待校准，调度沿实际资源和任务耗时工作。人工请求等待已有任务排空，采样仍繁忙时返回原因，另行手动重试。

Miter/s 是该固定混合负载的工作单位，不是 FLOPS。只有同版本基准参与比较；同标签真实任务耗时用指数移动平均逐步替代先验。AVX 等指令集差异由实测反映，不套人为倍率。

该基准是单Python进程内的多个NumPy调用线程，BLAS内层为1；其峰值适用于这个内核。独立SPICE/RTL进程、编译与大矩阵使用各自同工作量吞吐/核时对照，调度预算继续由操作员配置，基准峰值不构成通用并发上限。CPU百分比以系统可见逻辑CPU为分母；虚拟机中这是vCPU数，与宿主实核及DCO预算分别解释。

## 生命周期与终端实现

持久状态根保存输入、回执、检查点、资产和未领取输出；可重建 TMP 放共享 RAM 或显式磁盘 temp_root。任务成功、异常、取消及服务退出都按进程/任务所有权清理；待领取结果与中断恢复引用继续保留。迁移前核对 reparse point，普通文件与链接元数据分别处理，不沿链接目标移动共享工具。

Windows 外部任务 TMP 设置与输入相同的低完整性写入标签，父目录 ACL 保持。Linux 进程监控共用 250ms 快照，退出/取消使用请求后开始的新扫描并跟踪另建会话的原生子进程。连接槽按 FIFO 排队，本地 PoolBusy 表示尚未发出请求：保留原 ID 和授权等待，取消时释放。

看板宽度达到 120 列时左侧资源/份额、右侧逐任务，窄窗改上下分区；每任务独立一行，4位ID仅作展示。底部固定用法/候选/分隔/输入四行，极矮窗口优先输入。使用真实视口高度、ASCII 边框、实际字符单元宽度，按绝对坐标只画变化行。Windows 经典控制台启动尝试 160×50，并尊重屏幕上限、已有大窗口及 ConPTY 宿主尺寸。切换备用缓冲区、清屏和完整首帧合为一次输出；写完后仅请求可见经典控制台重画一次，不擦背景或等待宿主。之后保持变化行刷新，界面交接保留原屏幕，ConPTY 的窗口绘制由宿主负责。

资源表头采用 `CPU U/B`、`RAM U/T`、`RSS/Res`，工程份额采用 `Share/Pri`、`Jobs/CPU`；面板标题说明逻辑线程与GiB单位。着色识别实际列布局，包括可选Share/Pri及所有线程数量；数字ID保持青色，Tag内部不解析数字、状态词或十六进制词。回归直接渲染各宽度的真实任务行，覆盖纯数字ID与标签边界。长阶段名和整串seed仅在显示时压缩，如`AB s23 FACE Q256 tt27`、`shelfT4 s71 16k`，原请求标签与完整seed不变；任务Tag原则见“分配策略”。

Windows CPU信息通过注册表和`GetNativeSystemInfo`读取，终端可见性/焦点共用Toolhelp快照；启动首帧不等待WMI/CIM查询，架构名称与校准缓存保持一致。

托管父进程和服务子进程各自持有防休眠请求，覆盖子进程重载边界。Windows 使用 `PowerCreateRequest` 持有 SystemRequired/ExecutionRequired，操作员可用 `powercfg /requests` 核对具名 DCO 原因；Linux 的 systemd-logind 环境使用 `systemd-inhibit --what=idle --mode=block`，由随上下文退出的标准输入管道管理辅助进程。异常路径归还已取得的请求与句柄，显示器不要求常亮，一次性客户端操作不持有抑制请求。

耗时命令和文件操作后台执行，完成后及时释放 future/句柄；补全只读快照，Enter 才执行。键位与实际操作集中在 README。
