# DCO 接口与设计

## 责任与入口

DCO负责准备、排队、能力路由、CPU/RAM/加速器分配、实际执行、领取和原ID恢复。工程提供业务工作、冻结输入、真实有用并行上限、能力和内存需求，并负责科学测量、评分、有限预算、结果解释与持久发布。

`max_cpus`是整批任务的并行上限，当前映射需求由在途项数、可启动项数及子项数值阶段需求共同决定。全部输入已经启动后，单线程映射按剩余在途项数收缩授权；声明`item_max_cpus`的进程映射可把余核用于子项数值阶段。终端`CPU/max`分别显示当前授权和整批上限。核对扩核应同时查看原ID的`requested_cpus`、`active_cpus`及逐项启动/完成记录。

| 模块 | 职责 |
| --- | --- |
| `tasks/client/pipeline` | 任务声明、工程SDK、持久准备与收齐 |
| `execution` | 映射及数值内核执行，实际进程/线程宽度和尾项回收 |
| `coordinator/allocation/admission` | 队列、兼容资源、工程份额和准入窗口 |
| `worker/process/resources` | 进程树、工具环境、真实用量、临时文件 |
| `leases` | DCO执行器内部资源协商 |
| `bundle/acceptance/cleanup` | 不可变内容、原ID受理、引用与领取清理 |
| `commands/console/view` | 命令语义、交互和展示 |
| `cli/startup/terminal` | 启动、可见终端和重载 |

服务、SDK和终端仅依赖Python标准库；计算函数使用节点已登记的科学环境。工程通过中心提交，不读取节点清单或指定设备。操作员维护节点、预算、工具、解释器绑定、证书和共享目录。

## Python接口

公开任务只声明`max_cpus`，省略时为1024。串行工作声明1；单代、种群及有限输入集合声明真实有用上限。任务没有`cpus`、最低核数或auto开关。实际`cpus`只出现在DCO授权、状态和回执中。

```python
from remote_compute import Client, python_map

client = Client('http://127.0.0.1:26133')
plan = {
    'seed-1': {'task': python_map(
        'business:evaluate', inputs,
        max_cpus=len(inputs), requires=['ng47'],
        base_memory_mb=128, memory_per_cpu_mb=768,
        timeout=3600),
        'files': {'business.py': business_source}},
}
results = client.execute(plan, project='my-project',
                         output_dir='runs/current/dco', publish=publish)
```

`business:evaluate(item, **kwargs)`是可导入函数。业务文件作为输入或内容资产提供；源码、模型和数据分别复用。`python_map`保留输入顺序，默认每个输入运行于独立子进程，每项使用1核；完成即退出进程并释放其分配器/模型内存。DCO自动调整同时在途的输入数，工程不维护执行池或借核循环。单项多线程数值内核使用`python_call`，或由业务定义可复用的数值内核边界。

`python_map(..., backend='thread')`使用同一解释器内的线程，适合释放GIL的原生调用及必须共享的缓存；线程数仍由DCO管理，单项数值库限制为1线程。线程后端中的闭包、模块状态和对象缓存可共享；进程后端需要可导入顶层函数或`module:function`。纯Python CPU计算使用进程后端。

已有业务入口可以用`command(['${tool:python}', 'runner.py', '--workers', '${cpus}'], max_cpus=...)`。DCO在启动每一步前取得授权，再展开实际核数及数值库环境。任意外部命令在该命令边界使用其授权；需要运行中增减实际并发的输入流使用DCO映射执行器。

任务的`env`同样展开工具占位符；例如`env={'NATIVE_CXX':'${tool:cxx}'}`让Python入口使用当前节点已登记的编译器。原生源码、构建参数和二进制ABI分别记录；在执行节点生成本机库，或选择相同ABI的预编译资产，再由业务加载。基础C/C++不另申请能力，OS不包装成语义能力标签。普通任务禁止指定平台，由DCO在语义能力、工具和资产要求满足的提供者中放置。平台筛选仅供操作员调试，调试约束同时参与准入、资源规划、缓存匹配及加速器回退；worker在展开输入前复核。

在DCO任务内，业务入口可调用：

`max_cpus`声明任务本身理论上有效的最大并行度，应尽可能覆盖完整任务的有用宽度。54个可并行个体可声明54，广义可扩展搜索可声明1024；不按当前空闲核数、设备容量或四核起步策略压低原始申报。当前节点容量、共享配额和RAM约束由DCO施加。运输组规模不是任务内部并行阶段的统一上限。普通单层map的每项只用1核，因此其有用宽度由就绪项数决定；包含其他并行阶段的业务使用python_task及阶段limits表达，按真实就绪工作借还资源。

```python
from remote_compute import map_items, run_call
values = map_items('business:evaluate', ready_inputs, kwargs={'mode': 'native'},
                   limits={'base_memory_mb': 512, 'memory_per_cpu_mb': 896})
result = run_call('business:train', limits={'max_cpus': 8}, config=config)
```

`map_items`可提供`on_result(index, value, error)`，逐项持久化业务检查点；`python_map`在`.dco-results.json`写入已完成项及最终状态。直接任务声明的返回值须可JSON序列化，大数组、模型及科学记录写声明输出，返回其必要索引。默认映射项内部的嵌套调用共用该项的1核。

两级并行使用`python_map(..., item_max_cpus=8, max_cpus=80)`或`map_items(..., item_max_cpus=8, limits=...)`；默认`item_max_cpus=1`。多核子项使用process后端，业务在完成的评价批边界调用`run_call(kernel, limits={'max_cpus':8}, ...)`。父执行器先为未启动lane分配1核，外层就绪lane全部启动后，才把额外授权分给子项数值批；10条最多8核的搜索可申报80，有不同宽度时max_cpus申报真实有用宽度总和。子项阶段上限按自身有用宽度给出，例如普通串行项保持1。

父执行器独占分布式租约。子项通过每次映射私有的Windows named pipe或Unix socket接收父授权，不占TCP端口、不访问中心租约。父active floor含已承诺启动的lane及运行中的数值线程；待确认的缩核期间不复用未受保护的槽位。子项只从父已经确认的授权中取得额外核数；扩核RPC在途时继续使用已确认的1核，后续批次再使用增加的授权。只有1核可给时，子项读取私有共享状态，在需求变化时单向通知父级，稳定单核批次省去双向IPC。完成、异常和取消归还资源，线程设置先恢复1再归还阶段授权。独占整个任务的python_map在计算和发布完成后随进程结束其资源更新器；退出不等待可选扩核的迟到回执，worker沿原任务ID释放全部授权及待处理租约。入口内的map_items阶段仍收齐阶段资源归还后交接下一阶段。内存由父map的聚合声明/limits及DCO实测标定管理；子项run_call的limits仅声明max_cpus，避免把共享父基线重复计入每个子项。业务数值库的线程数必须跟随本批实际REMOTE_COMPUTE_CPUS；SDK调整已加载的Numba/Torch/BLAS线程，Numba初始池上限保留item_max_cpus。DLL控制器在导入状态变化后重建，稳定批次复用控制器；单核快路保留批后轻量复位。

任务`timeout`覆盖整个运输的执行墙钟时间，与网络RPC超时分开。worker向整个子进程树提供同一单调时钟期限`REMOTE_COMPUTE_DEADLINE`，回执`deadline`记录对应UTC时间戳。`remaining_time()`返回剩余秒数，在DCO任务外返回`None`；`check_deadline(reserve_seconds=...)`在剩余时间进入业务落盘预留时抛出`TimeoutError`。业务在真实评价与记账边界检查，沿既有异常路径发布已付前缀、原ID和恢复索引。预留属于原任务时限，硬时限保持。

`.dco-results.json.items`保存已返回结果；独立的`item_states`按原输入索引记录`pending/running/succeeded/failed`及起止时间。SDK在启动前持久标记该输入的执行尝试；进程树退出后，worker将仍在运行的项标为`interrupted`、未有启动尝试的项标为`not_started`，保留完成结果，顶层状态与运输终态一致。评价次数沿业务账本读取。框架记录执行身份和输出，科学数组与付费前缀由业务及时发布；硬终止后的未知付费量保留为未知。

中心操作员使用`client.control(job=原ID, priority=整数)`调整已受理排队任务的调度优先级，取值范围沿任务priority规则。`submitted_priority`保留原声明，`dispatch_priority`记录有效覆盖；覆盖持久保存并在中心恢复时生效。原request.zip、请求SHA、科学输入、种子、费用和原ID保持。运行中及终态任务保持其调度与执行状态。priority在工程之间对新任务全局排序，同级再按resource_share分配；新任务的priority不得跳过已有任务的前四个有用核。工程内分层安排须同时核对跨工程份额。

`python_task(function, kwargs=..., max_cpus=...)`运行串行业务入口：初始只占1核。入口在独立GP、角点或其它真实并行阶段调用`map_items`，DCO按真实需求动态授权，结束后归还至1核再执行串行训练等步骤。它适合一个搜索内部有多个并行阶段的工作流；`python_map`用于相互独立的完整输入，默认单项1核、可声明进程子项内核上限，`python_call`用于一个多线程数值内核。工程只表达业务阶段，不维护租约或进程池。

`iter_items(function, items, backend=..., stop_when=..., limits=...)`提供完成顺序的`index/value/error`流，用`with`管理。在途项与尚未消费的结果合计受实际取得过的并行窗口限制，不按输入总数积压。消费者发布和业务判定不阻塞空槽回收，结果窗口满时停止新增并归还空闲CPU。预算门触发调用`stream.stop()`停止新增，继续迭代收齐已在途结果。

提前离开上下文时，SDK收齐已开始的工作，将未消费记录的原索引、输入、结果和错误保存到声明输出`.dco-streams/`，并抛出`StreamResultsPending`；其`results/recovery_dir`供业务继续发布。正常消费完毕不生成该目录。恢复记录为本任务可信pickle文件，工程持久发布后随运输副本回收。

串行业务编排使用`python_task`；在原有排空边界进入训练时，`run_call`先等该原ID的SDK stream完成资源归还并检查错误，再取得数值阶段授权。仍有未启动输入的活跃流应先收齐或停止并排空，避免等待消费者自身而死锁。`run_call(..., limits={"max_cpus":8, ...})`声明阶段有用上限和可选内存需求，不改变父任务上限。

`map_items`、`iter_items`和`run_call`均接受阶段`limits`：`max_cpus`取父任务上限内的有用宽度；内存使用固定`memory_mb`或`base_memory_mb + memory_per_cpu_mb × 实际授权CPU`模型，线性模型可加`memory_limit_mb`。省略内存字段时继承父任务模型，显式内存字段替换本阶段模型；父任务声明和后续阶段默认值保持。映射在第一项启动前完成该阶段资源协商，随后按真实在途与就绪项扩缩；尾项结束归还空槽及对应RAM。已知冷编译峰值须由父任务首槽容纳，数值阶段按实测工作集声明，避免把编译预留沿用到每个并行数值项。

## 持久准备与收齐

`Client.execute(requests, project=..., output_dir=..., prepare=None, publish=None, ready_tasks=None, stop_when=None, cancel_when=None)`同步执行有限业务计划，直到已受理原ID收齐。独立output_dir在同进程或不同进程中并发调用；相同调用目录、中心URL和project共用待收窗口。共享状态索引位于调用目录`.local/dco-client/`，工程文件锁只覆盖该索引的短读改写。准备、计算、网络查询、领取与业务发布回调均在工程锁外执行；每个output_dir保留原ID恢复所需的单写入者锁。不同批次保留同一project及公平份额。

- `requests`为业务键到请求的映射，或`(key, spec)`序列；业务键非空且唯一。
- 业务请求为`{'task': task, 'inputs': directory, 'files': mapping}`，也可由`prepare(spec, original_id)`返回。依赖包装为`{'spec': business_input, 'after': [keys]}`。依赖图在受理前校验。
- `after`等待前序结果完成持久发布，之后才准备后续输入。独立任务继续准备和执行。
- `Deferred(reason)`表示输入暂未就绪，立即归还准备线程；同一次`execute`中，该项检查完成后至少间隔1秒沿原ID重试，其他项完成不缩短此间隔。重新启动管线时沿原ID重新检查业务门。`Skipped(reason)`表示业务门已决定跳过，在结果的`skipped`中登记，不生成科学回执。
- 新满足依赖的项和到期重试按原catalog位置合入就绪队列。有首次就绪项等待时，最多连续准备3个重试项，再给首次就绪项一次机会；准备完成和远端执行仍可并行。
- 同进程同工程共用4个准备、2个提交、2个领取/发布线程；跨进程共享待收额度。每次调用只等待自己拥有的工作收尾，发布慢不会阻止其他批次完成。`publish(receipt)`可能并发调用，须按原ID幂等、线程安全，成功返回前持久发布科学输出、费用和恢复状态。准备/发布回调不递归执行同工程计划；业务依赖使用after表达。
- 每项`state.json.collection_timing`记录进入收集队列的时间、实际排队、fetch、回执写入、发布及删除耗时；transport分项包含ZIP准备轮询、请求、解码、解包和字节数。计时属于本地运输状态，不改写原回执或科学数据。`client.last_fetch_timing()`读取本线程最近一次fetch的本地计时并标明原ID，不发起RPC；历史记录缺少的分项保持未知。
- 默认窗口覆盖兼容线程并超过128；`ready_tasks`可设1–4096，并发调用须取相同值，通常全部省略。准备中、受理未明及已受理未完成发布/删除的原ID共用额度；发布失败的原ID跨控制器恢复继续计入。接续待恢复目录领取原结果后再补位。工程只提供已授权且真实就绪的工作，不为填队列增加评价或越过依赖。

共享索引保存各输出目录的在途原ID及其状态位置。新控制器在原输出目录无人持有时核对持久状态，归还已退出准备者的未用额度，继续保留受理未明和未发布结果；冷状态读取在工程锁外进行。进程退出由系统释放文件句柄，锁文件本身保留复用。

`output_dir`保存计划、按业务键划分的状态、原请求ID、冻结请求、回执和已领取输出。原ID先持久化，再准备/提交。相同输出目录只能接续同一业务键、声明输入、原ID及依赖计划，变更会在提交前拒绝；准备完成的输入以冻结请求为准。路径表示输入位置，内容身份由业务spec或资产ID声明；接续不重新调用准备函数改写已冻结字节。

收齐顺序为`fetch(delete=False)`、持久回执及输出、业务`publish`、远端`delete`、回收已消费请求包。DELETE按原ID幂等确认：404表示已释放；运输错误或502/503/504后先核对该原ID，仍为终态时最多补发一次DELETE，运行中或权限/冲突错误直接返回。确认失败保留published状态供原目录续收，不重新计算或重复科学发布。发布失败保留已领取原结果；接续只重试发布，不重算。提交回应丢失查询同一ID及输入摘要，恢复保持原请求字节。已受理任务消失时保留失败和恢复事实，不创建新科学身份。

隔离的可重入python_map/python_call/python_task遇到实测内存压力中断时，中心沿同一原ID和原请求字节独立恢复，最多2次，分别退避5/15秒，再按先前实测工作集和当前兼容设备的安全余量准入；警戒或恢复稳定期的设备不接资源恢复任务。resource_recovery_limit与resource_recovery_count单独写回执，retries=0不禁止这一资源恢复。retries继续控制其他基础设施中断；默认上限为2，显式值保持。业务进程失败、用户取消不重算，原生命令和具外部cwd的机器操作保持原显式策略。科学输入、种子、参数和原请求不改写，物理成本作为恢复开销累计；未知费用/评价前缀保持未知，不追加新的科学实验。

资源恢复先在调度锁外取回本次原回执及声明输出，再原子转回原ID队列；取回失败保留明确的中断与恢复错误。map复用.dco-results.json已发布的成功项，按原索引继续未完成项；连续中断前尚未进入正文时仍保留先前成功快照，已成功项和文件不因空快照消失。声明的检查点和输出沿恢复运输传递，冻结输入文件不被覆盖；entry/call内部未发布为独立map项的工作保留为未知前缀，由其既有检查点语义续接。到达资源恢复上限后停止新尝试，已成功项、原回执、输出及失败事实仍可领取。wait/execute持续跟踪同一ID，attempts及.dco-attempts保存每次尝试，total_cpu_seconds累计已付CPU；最终发布后统一释放运输副本。

远端明确以4xx拒绝，且原ID查询确认为404时，立即归还准备额度，冻结请求保留供同目录接续。受理未明及已有ID身份冲突继续保留原状态；缺失的历史原ID须提供其持久回执后再完成领取和释放额度。

已有ID可声明`{'job_id': original_id}`。若原ID已领取并删除，同时提供`receipt`字典或路径；业务负责该回执引用的持久成果。SDK不重新准备或提交这些原ID。

`stop_when()`返回真、中心关闭新增受理，或Ctrl+C时，管线停止新增，继续收齐已受理任务，再抛`ExecutionPaused(results, remaining)`。恢复使用相同计划和输出目录。单项准备、提交、执行或发布失败只阻塞该项及其after后继；独立就绪项继续入队、计算和发布，最后集中抛`ExecutionFailure(failures, results)`，其remaining和blocked列出恢复入口。未发布原ID继续占用待收额度；本次无在途工作且额度已被未发布错误占满时返回失败，避免等待自身释放额度。已有完成项保留。`ExecutionResults`为回执列表，含`skipped`业务键。维护门关闭期间也能领取恢复的原ID。准备、提交和发布阶段的中断同样保留原ID；已领取但发布中断的项留在remaining，接续完成发布后再删除远端回执。

`cancel_when()`返回真后，本次调用停止新增，并沿自己已受理及提交竞态中受理的原ID请求取消；同工程其他调用继续。锁存取消时，提交中与已受理原ID的取消意图先写入状态，POST前再次核对；恢复时仍会完成取消。带取消标志且原ID查询404的项保留remaining，释放未受理额度，保持原ID和请求供业务核对，不重新POST。所有终态回执继续fetch、publish和delete，声明的部分输出与费用保留。主动取消的cancelled回执计入已收齐结果，其他执行失败和发布错误仍抛ExecutionFailure；若有未受理项，抛ExecutionPaused并列出remaining，全部收齐则返回回执。stop_when、维护及Ctrl+C本身不请求取消。业务条件和发布回调须支持并发调用。

## CPU与内存

内存需求分别核对解释器和依赖的常驻基线、输入及缓存、优化器状态、计算工作区与后处理峰值。一个完整优化工作进程的RSS不等同于一次目标函数评价所需内存。线程共享的基线只计一次，独立进程的解释器和依赖按进程数计；`base_memory_mb`与`memory_per_cpu_mb`按实际执行拓扑声明，不采用统一的数学任务MiB/核常数。

中心按每个设备分别限制相邻任务派发，worker限制每个任务的首次进程创建：普通任务最少间隔0.5秒，超发任务最少间隔1秒；与超发启动相邻的间隔至少1秒。设备之间独立派发。启动等待使用设备独立互斥与可取消等待，不持全局调度锁；已运行计算、资源协商和结果领取继续并行。同一任务的后续命令不额外等待启动间隔。

调度始终按三步执行：已有弹性任务先取得最多4个有用核；再让新就绪任务以1核进入运行；没有更多可进入的新任务时，剩余兼容核心继续分给已有有用工作，尽量用满所有核心。新任务的priority不改变这三步顺序。工程目标CPU数不构成配额。priority决定新任务优先级，同级按当前占用线程数除以resource_share排序，随后优先较小启动宽度；max_cpus是有用并行上限，不用于惩罚可扩展任务。真实就绪能力、设备CPU/超发上限、RAM及加速器约束实际分配。

基础CPU配额由本机cpus配置给出，cpu_limit限制可配置的基础配额。主机已报告的CPU授权达到基础配额且CPU利用率低于90%时，临时上限为floor(基础配额×cpu_overcommit_factor)；该倍率默认1.5，允许1–1.5，1表示关闭超发。倍率始终以基础配额计算，不以已扩大的上限继续相乘。中心节点limit进一步限定该节点的基础配额，并使用相同倍率。尚待启动的运输预留不触发超发。

临时上限只作为同一调度器的容量输入，继续遵守三步顺序、任务max_cpus、真实就绪需求和RAM/加速器准入。CPU达到90%或缺少有效CPU采样时，上限回到基础配额；新任务及新增授权停止使用超发额度。已有活跃工作线程保留授权，完成事件与资源协商归还空槽，因此实际在途数可暂时高于回落后的上限。health的base_cpus与cpu_overcommit_factor记录基础配额和倍率，cpus记录当前临时上限；节点汇总同时给出base_capacity与capacity。

终端CPU U/B的B固定取base_capacity（直接worker取base_cpus），括号显示系统逻辑线程数。动态capacity不代替基础预算。cpus命令保存基础配额并分别反馈基础预算、当前准入；nodes明细同时列出两者。超发时授权数可以超过B，原配置和在途授权保持各自语义。

映射执行器在完成事件和最长1秒的等待间隔报告实际在途数与就绪数；中心只回收未被在途计算占用的槽。资源RPC在执行器独立管理线程中进行，已授权输入继续计算。外层并发和内层数值库线程共用一份预算。单个剩余映射输入只保留1核，单个多线程内核在其安全边界取得有用宽度，并登记实际活动核数；嵌套内核沿用外层所有权。

每个映射阶段先取得当前CPU/RAM授权，再在同一把本地锁下确认并预留启动槽位；预留项立即计入资源快照。开始标记持久化、进程创建和结果回调在锁外执行；资源协商期间的新启动受已报告的在途下限约束。缩核完成后按新授权预留，授权校验保持严格，实际在途数不被截断或改写。

内存使用以下两种声明之一：

```python
python_map('business:evaluate', items, memory_mb=4096)
python_map('business:evaluate', items,
           base_memory_mb=128, memory_per_cpu_mb=768,
           memory_limit_mb=8192)
```

固定`memory_mb`默认为256MiB。模型使用`base_memory_mb + 实际授权核数 × memory_per_cpu_mb`，可选`memory_limit_mb`限制阶段调度包络。声明量用于冷启动和阶段切换估计，稳定运行后固定与线性模型都按任务树实测校正。进程映射完成项退出后，其内存归还；线程共享缓存仍由实际RSS计账。Windows物理RSS与PrivateUsage分别计账，不把已提交但未驻留的页重复扣留。设备预算、系统保留与实时headroom分别记录；看板RAM U/T为物理用量，Admit为可派发额度。 任务列RAM实/报显示当前任务树RSS与按当前授权核数计算的原始阶段内存估计；校准预留保留在API和明细。两项统一以GiB计算，隐藏单位，保留1位小数，小于0.1显示0.1；缺少数值时显示-。

`memory_mb`与`memory_limit_mb`不设置进程的OS硬内存限额。初次准入允许最多每槽256MiB的冷探测资金，估计超过设备容量仍可按原ID进入队列并取得首槽；未量测的在途派发继续占据账本，防止并发重复花费。取得至少2秒、3次有效任务树采样后，固定和线性模型使用最近10秒RSS/private各自的峰值；包络取峰值125%、峰值加32MiB、峰值加最近2秒正增长速率的2秒增量三者最大值，并覆盖当前实占。

CPU数与RAM独立计账。采样记录该包络期间报告的最大实际活跃宽度，短项之间的空槽保留采样。只有一个有效宽度时，固定估计使用整树包络；线性估计在尚未测出共享基线与并行增量时，按完整实测包络除以实测活跃宽度筹资每个槽位；声明基线不参与这次分解。明确零增量或已经测得零增量的共享阶段按整树包络筹资。取得不同宽度的稳定包络后，固定与线性声明都按实测增量校准：每核增量取宽度之间的非负内存增量率，基线覆盖剩余工作集；共享内存不随扩核增长时，每核增量可为零。不同宽度最多保留8份，窗口10秒；过期数据退出，已有同阶段增量成本随当前包络重新定基线，避免已退役峰值长期占用准入。增长先取得CPU/RAM授权，再启动进程；新宽度的采样预热期沿用同阶段已校准成本，单纯预留量重定价保留有效采样。外部命令或内存阶段切换清除上一阶段学习值，未取得有效宽度时沿声明估计。估计仅阻塞扩展时允许已筹资的首槽继续探测，多活跃槽探测按完整活跃宽度筹资，活跃线程保留原授权；信用与可用额度合计受节点容量限制，worker本轮授权不超过中心本轮已预留预算。 同一已确认且稳定校准的固定/零增量阶段，实际RSS/private仍在可用已筹资额度内时，worker使用已有采样余量扩核，本轮RAM授权保持在中心预算内；学习值保留原始更高包络。新阶段、实占超预算和正的每核增量继续按完整模型核算。

worker按实测物理与提交余量分级保护。低于物理总量2%（下限128MiB，上限1GiB）进入警戒，停止新增任务和额外并发授权，命令、item和数值批在安全边界等待2秒；提交余量仍低但已稳定且高于128MiB时，已有授权可继续计算。物理余量低于警戒线，或提交余量低于128MiB并持续2秒，才允许回收任务；任一真实余量不足32MiB时立即保护。单次低样本不触发常规终止。余量恢复后稳定2秒再放开新增；已运行线程不被中途撤销。

确需终止时仅在同一主机的实测消费者中，按低priority优先、稀缺资源占用较大优先，每2秒至多选一个任务树。回执保留压力采样、保护阶段和受害者priority，资源中断使用error_kind=memory_pressure；等待资源耗尽原执行时限同样归资源中断，业务失败和用户取消分别处理。原ID、声明输出、成功项、未知前缀及累计费用沿上述恢复与领取生命周期保留。主机的分页文件、安全设置及非DCO进程不由此策略修改。

原请求、输入身份及声明量保留；实际物理和提交预留分别记录为`memory_reservation_mb`与`memory_commit_reservation_mb`。未发布或仍被原ID引用的科研输出保留。

资源调整POST遇到连接故障、网关超时或原请求仍未结束时，SDK先观察同一执行尝试的状态；polling租约等待原`resource_request`结束，再有界重试同一资源调整。任务终态、权限错误及永久资源拒绝立即返回；重连遵守原任务期限。此过程不重新提交计算，不消耗或扩大科研重试预算。
CPU/RAM增长先预留，远端确认后提交；减少确认后归还。同一原ID串行资源变更，网络RPC不持全局调度锁。成功授权以`memory_phase`记录原始阶段声明，实际筹资量单独记录；中心轮询保留本轮刚确认的阶段。资源协商明确返回内存不足或中心回复超时、同时保留原授权时，SDK读取当前执行尝试的授权，polling通路使用当前worker尝试ID。同一已确认阶段使用已获CPU和实测内存授权继续执行，并按原间隔重试扩核；尚未确认的阶段若与执行环境中的冻结父模型相同，先保留原授权中按模型可用的完整宽度；原模型筹资不足时仅维持其已在途授权宽度，不新增启动；已完整筹资的空槽继续按原授权补位，尚未启动且仅估计阻塞时保留一个已筹资冷探测槽，下一秒继续扩核协商；不同阶段按当前声明核算所需内存。原授权不足以覆盖活跃线程或一个有用执行单元时保留资源错误；终态及其他冲突同样直接返回。利用率用于放置与诊断，不把低利用率当作可强抢在途核心的依据。真实有用需求和执行器边界负责释放闲槽。

拒绝资源调整后的授权查询发生暂时网络故障或502/503/504时，同阶段可沿用最近一次已校验可用的CPU/RAM；内存拒绝保留已确认宽度，中心调整结果未明时仅保留其活跃底线（最少1核），随后继续查询。构造时的CPU种子不构成确认授权。首次授权或阶段改变时，仅有界重试读取，并服从原任务的单调时钟期限；不重放计算或扩大显式retries。已读到的终态、权限及其他永久错误直接返回。

`resource_share`为`(0,16]`，`single_thread_weight`为`(0,8]`，`priority`为`-1000..1000`。窗口查询的`queue_ratio`为`[0,4]`；默认供给深度让就绪工作持续排队。

同一规划操作复用相同任务形状的能力匹配、RAM计算与分配度数；缓存不跨提供者状态更新。语法解析LRU有界为256条。

## 运行能力

| 能力 | 含义与独立理由 |
| --- | --- |
| `ng47` | ngspice 47数值协议；可按需安装的电路仿真后端 |
| `hsp` | HSPICE后端；独立安装和许可条件 |
| `chisel` | 完整Chisel生成工具链，包含JVM/Scala及RTL生成依赖 |
| `ml` | Torch及图学习环境；依赖体积较大，可在最小节点省略 |
| `cuda` | 可分配CUDA硬件和对应运行环境；与CPU Torch区分 |
| `layout` | GLayout/GDSFactory、Magic、Netgen的版图与后仿工具链 |
| `rtl` | Verilator或Icarus独立RTL仿真工具；已有RTL可直接执行，省去JVM/Scala依赖 |
| `onnx` | ONNX Runtime/OpenCV CPU推理环境；无需完整Torch训练依赖 |

Python/C++为基础环境，不列能力。禁止包组合、设备、OS、工程名或构建后缀。工具链必须在单节点完整，不能跨节点拼凑可用性。Python统一`${tool:python}`，由操作员`python_runtimes`绑定CPU、ML或已授权CUDA解释器；路径和工具argv只在操作员视图及原任务回执保留。

普通工程查询`client.capabilities()`，返回汇总语义能力、CPU/RAM总量和无设备ID的加速器档案。普通提交、能力和准入接口明确拒绝平台指定；操作员调试可过滤平台并查看设备清单。`shared:alias`是明确的数据位置要求，用于`${shared:alias}`；源码、数据及模型优先作为内容资产，不把共享目录名称包装成运行能力。

GPU任务声明`requires=['ml']`及`accelerator={'kind':'cuda', ...}`。默认整卡独占；`sharing:'memory', max_jobs:2, memory_mb:...`表示每任务显存预留，同时受卡容量余量和参与者最小max_jobs限制。CPU回退显式声明`fallback_after_seconds`；无在线兼容GPU时立即回退，排队达到阈值时沿同ID回退。首次派发后执行选择冻结，回执保留请求及实际加速器。

## 任务、内容与结果

公开任务包含`steps/max_cpus/timeout/outputs/env/assets/render/label/priority/requires/memory_mb/project`等业务需求。内存模型保存在`memory_model`，托管函数保存在`execution`。`node/platform/cwd`及机器操作仅供操作员调试，SDK和HTTP服务均检查该边界。

| 占位符 | 含义 |
| --- | --- |
| `${tool:python}` / `${tool:ngspice}` | 任务所需环境中的实际工具前缀 |
| `${cpus}` | 本步骤实际授权CPU数，在启动前展开 |
| `${work}` | 本任务输入/输出目录 |
| `${asset:name}` | 引用的不可变内容资产 |
| `${shared:name}` | 操作员登记的共享位置 |
| `${dco}` / `${exe}` | 平台源码目录 / 当前系统可执行扩展名 |

命令、环境及内容引用在受理时冻结；核数在步骤启动时按真实授权展开。映射子进程继承该任务冻结的完整Python启动前缀。`render`仅渲染声明输入文件。`outputs`相对任务目录，支持通配符。普通计算使用独立工作目录，`stdin`为输入包内相对文件。工具链、模型及大数据不随每次源码快照重复复制。

`sync_files(..., content_id=..., job_id=...)`按不可变内容同步。并发准备相同内容共享一次打包和传输，各原ID分别登记引用。SDK管线将原ID传给`prepare`供资产同步使用；未受理准备放弃时释放其引用。已受理和未领取内容持续保留。状态、引用资产和结果在普通磁盘，可重建工作与TMP使用任务专属RAM目录，正常、失败、取消均回收自有临时物。

接受后相同ID和同输入只执行一次。状态查询使用原ID的`statuses/wait_any`或有界分页；普通工程结果去掉设备名、URL、工具路径，保留本任务科学身份、资源、状态、时间、输出和费用。任务日志与声明输出按原ID领取。Windows领取与持久状态使用扩展路径命名空间，覆盖超过260字符的嵌套输出；领取失败保留原ID，修复路径后领取，不重算。

SDK在`GET /jobs/<id>/artifacts`携带`X-DCO-Artifact-Poll:1`，中心按原ID准备远端ZIP，未就绪时立即返回`202 {id,status:"preparing"}`。同一原ID共用一次准备，同一提供者串行传输；ZIP验证身份后原子缓存。SDK准备轮询从0.2秒开始，间隔最多0.5秒，每次有效准备确认续接观察；网络故障仍使用独立的有界重连。准备失败以409结束本次领取，保留原结果供下一次原ID恢复。准备线程参与服务收尾，原ID锁同时保护准备、领取和删除；控制及资源RPC不等待远端大包。中心及worker本地结果直接领取，完整ZIP仍支持ETag及断点传输。

`kill <id|all>`是终端唯一的任务终止命令；SDK和HTTP使用既有cancel接口。单任务支持完整ID或唯一的至少4位活动任务前缀。`all`固定执行时所连接端点的活动快照，沿原ID取消排队及运行任务，不枚举冷历史、不追杀后续提交、不改变受理或暂停设置。中心按原ID确认归属；worker只终止本设备任务。最多8个取消请求并行，统一等待最多30秒确认终态；远端取消未确认、原ID缺失或请求失败明确列入待确认结果，一次性CLI返回非零。原ID、输入身份、声明输出、日志及累计CPU费用保留。运维端重启使用`restart --wait`或`Client.restart(wait=True)`，在排空边界重载同版源码并保留原终端及状态根。

`clean`及操作员`POST /clean`在服务调度锁内固定当前queue中status=queued的任务，设置取消并摘出队列，防止派发竞态；不选运行、派发和已完成任务。目录、回执、尝试归档和临时物清理沿原ID锁，在全局调度锁外执行。原ID删除后返回404，索引删除标记防止重启复活。选中任务独占的资产缓存立即退出可访问命名空间并进入现有回收器；被其他任务、生产者、受理或上传引用的资产保留。新提交不加入本次集合，受理与暂停设置保持。部分失败保留可查询回执并返回原ID和错误；调用方不自动重提被操作员删除的计划。

## 门控、断连与回执

`control(accepting=False)`关闭新的工程受理，已受理队列继续派发、执行和领取；原ID幂等查询及操作员运维继续可用。`control(paused=True)`暂停派发，运行中的工作及资源协商继续。新增受理门原子保存到中心状态根，重启后继续生效。普通兼容修复集中验证并按节点自然空闲合并上线，保持全局受理；阻断故障或不兼容更新才使用一次有界排空维护。`start_paused`在进程调度线程启动前生效；维护完成清除配置并恢复保存的状态。

持久回执损坏按原ID修复：同目录隔离坏副本，保留输入、输出、引用及恢复来源；无可恢复完整回执时记录`failed/error_kind=receipt_corrupt`、未知费用和`cost_incomplete`。冷回执按原ID锁读取，内存最多缓存64份，目录递归操作在全局锁外。

设备60秒无成功握手后退出路由，停止普通任务轮询，保留原任务和授予；核心每60秒握手，最多5次，成功后沿原ID接续。人工停用不自动重连。未确认远端取消保留`remote_cancel_pending/cost_incomplete`，不把未知费用记0。`scan`是操作员显式局域网发现，最多4096地址、32并发，不参与工程设备选择。

任务环境`DCO_CPU_ACCOUNTING=1`启用已有进程组CPU采样，`cumulative_cpu_seconds`等于本任务用户与内核CPU秒；可用硬件频率时积分`Σ ΔCPU秒 × GHz`。来源、覆盖CPU秒和已观察工作量随回执保留，完整覆盖才给完整工作量。重试分项费用和总费用分别保留，缺测保留null。等待及空闲不产生CPU工作量。余额、credits和额度API不参与运行。

## 科研缓存与工程接入

AOP按原始角点及明文执行/测量协议交换；RGCN按完整逻辑观测交换；ARH与Bench沿各自生产者的缓存记录。`sync_cache`先比较清单，再以最多1024条或约1MiB补缺，不复制SQLite/WAL、任务认领或内部共享布局表。缓存键依据科学输入、协议与数据，不生成能力或引擎哈希。工程持久数据库、冻结观察和未验证历史身份继续由所属工程管理。

AOP按阶段选`ng47/hsp`；RGCN按阶段选`ml/ng47/layout`；ARH-DSE按阶段选`rtl/chisel/onnx/ml`；FIBER普通数值使用基础环境，Torch加`ml`，真实SPICE加`ng47`。设备覆盖和实际工具验收见[STATUS](STATUS.md)。各工程使用SDK管理准备与执行，科学输入、seed、评价次数、成本、已付结果和恢复身份跨段连续。

服务启动、设备配置、可见终端、TLS和运维命令见[README](../README.md)。运行预算以设备私有配置为准，实际版本以health和新PID核对。算力校准仅由人工命令触发，启动、重连和采样不运行基准。

启动通过原状态索引恢复任务；索引只保存紧凑身份及共享的资产字符串，终态回执留在原磁盘路径。不可变资产的展开大小保存在有界压缩的元数据索引中，重启不重复遍历每个内容文件；缺失的大小按实际内容补算。无本地监听者的空闲端口直接进入启动，已有监听者仍完成原服务识别。每个状态根的`startup-current.json`记录环境、索引、恢复及资产阶段耗时。

未被活跃任务、未领取回执或生产者引用的资产遵守512MiB暖缓存目标。淘汰先在同一文件系统原子移入私有`.trash`，后台回收实际文件，状态查询、授权和新内容同步继续流动。进程重启后接续回收已退役内容。服务取得状态根独占锁后，将遗留的资产上传目录及本worker临时命名空间中的原ID目录移交同一路径；其他工程命名空间、未知文件、科研回执和未领取成果保留。回收只删除入口自身，不遍历符号链接或目录联接的目标；待回收数量及有界错误保留在health。

操作员确认内容生产者已关闭后，可用`control(retire_asset=摘要)`退役一个中心输入，或`control(node=名称, worker={"retire_asset":摘要})`退役指定worker副本。操作与资源修改分开提交，校验完整资产身份；活跃、终态未领取及恢复任务、有效原ID交接、受理中输入与在途上传保持引用保护。校验、原子移名和缓存计数变更共用已有资产锁，递归回收使用上述后台生命周期。只处理指定资产，保留其邻居；已消失资产返回零字节。操作回执返回退役身份、存在状态和索引记录的逻辑字节数。

## 任务显示规范

当前任务显示`CPU/max`，分别为实际授权和任务声明的max_cpus；排队未授权为0。工程汇总的任务数/CPU用于比较工程负载。Tag最多24终端格，按对象、方法/阶段、必要设置、种子末2或4位、仿真/评价量或预计CPU秒组合最短业务摘要，例如`BGR PSL s26 ev:10k`、`Rocket RTL s01 ~90s`。CPU配置单列，Tag不重复项目列、不放整段或纯hash。显示按实际列宽作语义缩写并保留任务词，完整标签、输入和原ID仍在明细及回执。
